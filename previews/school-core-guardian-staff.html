F05 · 3 November 2026

Stable people records.
Explicit school relationships.

Guardian/student links and staff/section teaching assignments, with versioned changes and school-scoped history. These domain records prepare future authorization integration.

Scope and identity boundary

Protected operator commands register guardians/staff, correct their names/status, and create/update student links and section assignments. Names and school-owned codes remain private profile data. Matching names do not merge people. These are school-owned records: no login, identity-account binding, contact verification or portal permission is created. F02 integration remains deferred. Subject-specific teaching access, employment/payroll, guardian contact data, year activation and imports for these profiles are later work.

Six private tables

people.guardians / people.staff

Stable UUID, school-owned immutable uppercase code, private legal name, active/inactive status, version and timestamps. Codes are unique within each school and profile type. A name correction preserves the code and ID.

people.student_guardians

Stable link ID and immutable same-school student/guardian parents; relationship label parent/legal_guardian/caregiver/other, active/inactive state and version. One row per pair, including after deactivation. Labels record the operator's classification; they do not prove legal authority.

people.teaching_assignments

Stable assignment ID, immutable staff/year/section parents, active/inactive state and version. One row per staff/section pair. A composite school/year/section foreign key prevents wrong-year assignment. Multiple staff may teach the same section; there is no invented one-teacher limit.

people.relationship_events / relationship_commands

Versioned before/after metadata and immutable-in-command-interface retry receipts. Each event has exactly one same-school foreign key to its profile/link/assignment, with one event per target/version. Names and codes are omitted from snapshots/results; IDs and relationship metadata remain private.

Forward migration0007 preserves existing migration files/data. Every new table forces tenant RLS, including for its owner. Runtime and dispatcher roles receive no access. There are no cross-service foreign keys.

Command contract

All commands contain action, tenantId, requestId, operatorRef and reason. Use a private regular0600 JSON file, maximum16KiB. OperatorRef is a supplied label; the actual database role is recorded separately.

  • register_guardian / register_staff: code, legalName.
  • update_guardian: guardianId, expectedVersion, legalName, status.
  • update_staff: staffId, expectedVersion, legalName, status.
  • link_guardian: studentId, guardianId, relationship.
  • update_guardian_link: linkId, expectedVersion, relationship, state.
  • assign_teacher: staffId, academicYearId, sectionId.
  • update_teaching_assignment: assignmentId, expectedVersion, state.

Unknown/identity/contact fields reject. Parent IDs and codes cannot be reassigned; update existing inactive rows to restore them. No deletes or silent cascades.

State, concurrency and evidence

  1. Require the operator role, normalize/hash the command, lock the school/request key and set local tenant context.
  2. Exact retries return the original receipt. Changed reuse conflicts. Lock the school profile for new mutations, which require provisioning/active school state.
  3. Creating/reactivating guardian links requires a registered student and active guardian. Creating/reactivating assignments requires active staff and a draft/active year. Deactivation remains possible when those parents are inactive or a year is closed.
  4. Deactivating a guardian/staff profile fails while it has active links/assignments; remove those explicitly first. The shared school lock serializes profile/relationship races with academic and student changes.
  5. Expected versions fence updates. Stable IDs survive deactivation/reactivation. Domain change, history, security event and redacted receipt commit together or all roll back. SQL administrators remain privileged.

Verification

Test stable IDs/codes, same-school profile codes, multiple guardians/staff, relationship/assignment restoration, duplicate pairs, immutable parents, wrong-school/year references at service and database layers, profile/assignment races, stale edits, state guards, history/audit/receipt failure rollback, private output, forced RLS/role denial and absent HTTP routes. Run the complete core suite and fresh migration harness, followed by matching-head CI.
