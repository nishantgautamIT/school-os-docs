F05 · Core academic setup · 2 November 2026

Define the year.
Keep class identities stable.

First core-owned F05 slice: academic years, stable class levels and year-specific sections. Protected operator commands prepare draft configuration while cross-service school-admin identity integration remains deferred.

Scope and dependency boundary

F04 is not fully complete. Its merged provisioning/transport foundation is sufficient for isolated operator setup, but this slice does not enable a private portal or declare the full F05 dependency satisfied. No student/guardian/staff records, enrollment/imports, year activation, automatic rollover, attendance, fees or new HTTP routes. School profiles retain their existing pending/active identity state.

Four new tables

academics.academic_years

School UUID, stable year UUID/code, display name, start/end dates, draft/active/closed state, version and timestamps. New years are draft. This operator service edits draft years only; activation/closure are future workflows. Valid real calendar dates with end after start; no assumed April–March calendar or overlap prohibition.

academics.class_levels

School UUID, stable class UUID/code, display name and sort order, version and timestamps. Codes such as nursery, lkg or class-1 belong to a school and persist across academic years. Rename a display label without replacing its ID/code.

academics.sections

School UUID, section UUID, academic-year UUID, class-level UUID, code, nullable positive capacity, version and timestamps. The same A section can recur for another year/class. Composite foreign keys prevent references across schools; year/class/code are immutable in this service.

academics.setup_requests

School-scoped request UUID, normalized command SHA-256, action, original result, operator label and database role. Exact replay returns the original result, even after later edits; changed-payload replay conflicts. Identical request IDs in different schools are separate scoped keys.

All four tables force RLS even for their owner. No new table/schema access is granted to public HTTP or delivery-worker roles. Core owns these tables; there are no identity/engagement database references.

Command contract

Every command has action, tenantId, requestId, operatorRef and reason. Actions create_year/create_class/create_section return IDs and version1; update_year/update_class/update_section require entityId and expectedVersion. Full editable fields are supplied on updates; codes/parent IDs cannot be reassigned. Unknown fields, identity secrets, invalid dates/UUIDs, non-integer values and out-of-range PostgreSQL integers reject.

  • create_year: code, name, startsOn, endsOn. update_year: name, startsOn, endsOn.
  • create_class: code, name, sortOrder. update_class: name, sortOrder.
  • create_section: academicYearId, classLevelId, code, capacity (null means unspecified). update_section: capacity.

Year/class codes normalize to lowercase; section codes to uppercase. Unicode names are preserved and trimmed. Supplying a tenant ID is only safe because these commands require protected operator credentials; RLS alone is not user authorization.

One atomic operation

  1. Validate/normalize input and require the operator database role.
  2. Lock the school-scoped request, set transaction-local tenant context and check the original receipt.
  3. Lock the selected school profile; new mutations require provisioning/active state, not suspended/closed. An exact replay returns its historical receipt without causing another mutation.
  4. Resolve targets in the same school, require a draft year for year/section changes, and enforce the expected version on edits.
  5. Commit the domain change, durable audit event and receipt together. Constraint/audit/receipt failure rolls everything back.

The school lock serializes infrequent setup writes and makes optimistic version conflicts deterministic. Reads/writes use one checked-out connection. No deletion or published/private endpoint is added.

Validation gates

Real PostgreSQL checks: distinct school/year/class section identities; same-school foreign keys; RLS including owner/missing context; public runtime/dispatcher denial; replay/conflict/concurrent requests; version races; closed/suspended school and non-draft year rejection; audit/receipt failure rollback; valid leap days and impossible dates; capacity boundaries; protected CLI files/credentials; absence of new HTTP routes. Fresh migration/rerun and full core CI must pass before review. No new library is needed: use the existing Node24, pg transaction helper, built-in crypto and test runner.

Delivery status

Design recorded before implementation. Test evidence and PR links will be added here. Existing applied migrations and local school data must remain unchanged; this slice adds only forward migration0004. Full F05 and F04 remain open.
