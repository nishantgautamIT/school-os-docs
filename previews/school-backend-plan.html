School platform backend implementation plan

15 October 2026 · Proposed design · No production code or database implemented by this plan

Build one TypeScript backend repository with a NestJS/Fastify API, a separately runnable worker, PostgreSQL and private S3 storage. Keep module ownership explicit and deploy simply. The first production milestone should prove that two schools can use daily academic workflows safely, with recoverable records and dependable parent access.

This plan expands the supplied brief and existing backend blueprint into implementation decisions, records, request contracts, invariants and release gates. It preserves the full intended product; later modules are scheduled rather than removed.

1. Decisions and assumptions

Already selected: React/Vite/TypeScript frontend, Node.js/TypeScript/NestJS/Fastify backend, PostgreSQL, pg-boss workers, private S3 and a modular monolith. Nest documents a Fastify adapter; plugins and middleware must be compatible with that adapter. Nest Fastify documentation.

Additional proposed defaults: REST with OpenAPI; Drizzle over node-postgres for typed database queries, plus reviewed SQL migrations for RLS, constraints and posting procedures; server-side browser sessions; explicit transactional outbox; application-level permissions plus database tenant isolation. Drizzle exposes transaction handles, which fit the requirement to carry one scoped transaction through repositories. Drizzle transactions.

Use supported stable runtime/library releases, pin the tested combination and lock dependencies at implementation time. Do not select a preview version just to match a newer example. A short foundation spike must validate Nest/Fastify plugins, database transaction handling and the chosen pg-boss version together.

Planning assumptions: one customer school equals one tenant; browser/PWA first; an experienced primary developer; a small pilot rather than guaranteed capacity; imports from school spreadsheets; English and Hindi content; one school currency, INR, initially. A person can hold multiple school memberships and multiple roles. Multi-campus organisations remain a later extension; keep operational locations distinct from tenants.

The earlier ₹2,000–₹4,000 monthly allowance remains an unverified pilot budget, excluding substantial messaging, egress, payment fees, support and development. This document supplies no current provider quote.

Controllers validate transport input and invoke an application service. Services enforce permissions and transitions. Repositories accept an explicit transaction handle. Other modules call public services; they do not mutate another module's tables. Keep this enforceable with package exports and import rules. Shared packages hold mechanisms, not a universal business service.

Use synchronous calls for work that must commit atomically, such as a fee receipt and its allocations. Use durable events for PDF generation, notifications, projections and later integrations. A queue or object-store upload is never treated as part of a PostgreSQL transaction.

3. Module ownership and data boundaries

Use logical PostgreSQL schemas such as control, iam, school, school_finance and ops. Schemas organise ownership; grants, RLS and application checks enforce access. Platform invoices and school invoices have distinct tables and identifiers even if they share calculation utilities.

  • Platform: customers, billing contacts, plan versions, contract versions, subscriptions, commercial line items, platform invoices, payments, renewals, provisioning runs and support grants. Owns your business revenue and tenant lifecycle.
  • Identity: users, verified contacts, credentials, sessions, setup/reset tokens, school login identifiers, memberships, roles, permissions and scoped role assignments. Does not equate a verified phone with a verified guardian relationship.
  • Academics: academic years, class definitions, sections, subjects, section-subject offerings, teacher assignments and calendars.
  • Students: admission applications, stable student identities, yearly enrolments, placements, guardians, verified user-to-guardian links and student-guardian relationships.
  • Attendance/homework: attendance sessions and revisions; assignments, audience snapshots, submissions and feedback.
  • Fees: fee schedules, charges, concessions, payments, allocations, receipts, refunds and reversals. Owns student receivables before full GL exists.
  • Communications: notices, translations, approval versions, audience definitions, recipient snapshots, deliveries, attempts and action links.
  • Exams: assessments, schedules, paper versions, reviews, release grants, invigilation, attempts, marks revisions and report-card publications.
  • Resources: vendors, locations, consumable movements, assets/custody, book titles/copies, circulation and stock checks.
  • Procurement: requisitions, approval decisions, orders, receipts/inspection, returns and invoice-match exceptions.
  • Accounting: school chart of accounts, periods, journals, lines, receivables/payables, bank reconciliation and approved posting policies.
  • Media: upload intents, objects, event/gallery versions, audience policies, packages and expiring application grants.
  • Operations/AI: audit, outbox/inbox, idempotency records, usage and quotas; later AI requests, approved generations and cost reservations.

Public-school configuration should never share a response DTO with credentials, contracts or private finance data. Publish dedicated role-appropriate student and parent DTOs to prevent field leakage.

4. Tenant and identity design

A request's authority

For school endpoints: verify session → resolve selected school → verify active membership and access policy → check action permission → check class/child/resource scope → open scoped transaction → query permitted records. The school code or route tenant ID is a selector, not evidence of access.

Resolve bootstrap session/membership through a narrowly scoped identity access path that can only return the authenticated principal's memberships. Do not give all school repositories unrestricted access to all users. Platform endpoints use a separate guard and database role/pool with no default access to school records.

A trusted request context contains actorUserId, tenantId, membershipId, permissionVersion, requestId and optional supportGrantId. Resolve these server-side. Never accept role, actor, permission or support-grant validity from request JSON.

Database contract

Every tenant-owned table has tenant_id NOT NULL. Tenant tables expose a unique (tenant_id, id) key; child relationships reference both columns. Unique admission numbers, school usernames, receipt series and accession numbers include their tenant scope. This prevents an otherwise valid foreign key from linking School A's record to School B.

Illustrative RLS migration pattern, not a complete schema:

ALTER TABLE school.students ENABLE ROW LEVEL SECURITY;
ALTER TABLE school.students FORCE ROW LEVEL SECURITY;

CREATE POLICY students_tenant_scope ON school.students
  TO school_app
  USING (
    tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid
  )
  WITH CHECK (
    tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid
  );

Within one transaction and one checked-out connection, set parameterised context using SELECT set_config('app.tenant_id', $1, true). Pass that transaction to every repository in the operation. Reads also use the wrapper. No global mutable tenant state, no session-wide SET, no unrelated pool.query inside the transaction. Missing context denies tenant rows. PostgreSQL transactions must use the same node-postgres client throughout. node-postgres transaction guidance.

Runtime roles cannot own tables, change policies, truncate tenant tables, become migration roles or use BYPASSRLS. Workers use the same tenant transaction discipline. A separate restricted queue role handles pg-boss metadata; a privileged migration role is used only in deployment.

RLS here enforces school isolation. Teacher assignment and guardian-child limits are additional scoped application queries and policy checks; they are not satisfied merely by having a tenant ID. RLS is a second boundary, not a substitute for parameterised SQL or secure application code. PostgreSQL owners/superusers and referential-integrity checks have important RLS exceptions. PostgreSQL row security.

Accounts and sessions

  • One global user identity can have multiple memberships; school usernames are unique within a tenant. Do not automatically merge people because a family shares a phone.
  • Prefer high-entropy opaque browser sessions in Secure, HttpOnly cookies, with server-side revocation, idle/absolute expiry and rotation after authentication or privilege change. Apply CSRF protection to cookie-authenticated writes and a strict origin policy. Keep browser/API on a compatible same-site deployment where practical. OWASP sessions.
  • Use an established authentication library behind an internal interface, selected after a compatibility spike. Password storage uses Argon2id with parameters benchmarked on the pilot server. Never log passwords or setup tokens. OWASP password storage.
  • Setup/reset tokens are hashed at rest, single-use and expiring; consumption is atomic. Setup tokens are bound to the intended user and school. A temporary credential produces a restricted password-change session only.
  • Require MFA for platform administrators before live onboarding. Add school-admin MFA, rate limits and a documented recovery process; limit concurrent expensive password checks on a small host.
  • Parent verification requires an approved child relationship. A matching admission number or phone by itself cannot establish access. Relationship revocation affects the next authorised request and new download grants.
  • Role changes or membership suspension invalidate effective permissions immediately through a version check or fresh lookup; do not rely on a long-lived role claim.

Permissions are explicit actions, for example attendance.write, fees.refund.approve, exam.paper.release, report.publish, inventory.adjust and accounting.period.close. Assign scopes separately. A school administrator can operate the school but cannot erase audit history or bypass posted-record correction rules.

5. Core relational model and invariants

Use UUID identifiers, timestamptz for instants, local date for attendance/school calendar dates and Asia/Kolkata as the initial school timezone. Store exact decimal values in PostgreSQL; transfer money as decimal strings or integer minor-unit strings. Never use JavaScript floating point for financial arithmetic. Quantities may need fractional units and conversion policies.

Include created_at, created_by, updated_at and an optimistic version on editable records. Use purpose-specific cancellation/withdrawal states; generic soft deletion must not hide financial or historical evidence. Required identifiers and foreign keys remain normalised columns; JSONB is for bounded metadata, provider payloads and immutable snapshots, not the whole domain model.

Academic relationships

tenant → academic_year → section → section_subject
student → enrolment(student, academic_year) → placement history(section, effective dates)
teacher membership → teacher_assignment(section_subject, effective dates)
user → verified guardian link → guardian → student_guardian → student
attendance_session(section, date, session_type) → attendance_entry(enrolment)
homework_assignment → assigned enrolments → submissions → feedback revisions
  • Keep student identity stable. Enrolments record year-specific admission/roll/status. Placement history handles section transfers without rewriting previous attendance or teacher responsibility.
  • Default to one active enrolment per student per school academic year; model withdrawal and re-entry as explicit transitions and history.
  • Prevent overlapping active placements or duplicate subject assignments where the school policy forbids them. Enforce constraints in the database, not only in a form.
  • Attendance entries are unique per attendance session and enrolment. Entries must belong to the permitted section for that date; corrections retain actor, reason and previous state. Absence and “not recorded” are separate values.
  • Homework assigns a snapshot of eligible enrolments. Preserve assignment and submission versions; a later transfer does not silently rewrite the original audience. Apply an explicit policy for adding transferred students.
  • Import rows first enter staging, are validated and previewed, then commit in bounded batches. Keep import source keys and per-row outcomes so retry does not duplicate students or charges.

Indexes driven by access patterns

Start with (tenant_id, academic_year_id, section_id, status, id) on enrolments/placements as appropriate; (tenant_id, student_id, academic_year_id) on enrolments; (tenant_id, student_id, guardian_id) and the guardian-first counterpart for verified links; (tenant_id, session_id, enrolment_id) on attendance; (tenant_id, enrolment_id, due_date, id) on charges; (tenant_id, status, scheduled_at, id) on communication work; (tenant_id, entity_type, entity_id, occurred_at) on audit.

Validate exact indexes with representative queries and EXPLAIN (ANALYZE, BUFFERS) in staging. Include tenant columns in uniqueness rules and necessary child-side FK indexes. A list of indexes is a starting hypothesis, not proof of performance.

For All Students, allowlisted filters compose on the server. Attendance percentage requires a defined date interval and denominator; fee status requires defined due-date/cutoff rules. Join pre-aggregated tenant/enrolment projections rather than multiplying attendance and fee rows in a single naive join. Distinguish authoritative detail from asynchronously refreshed summaries and show freshness where material.

6. API conventions and representative contracts

Expose /v1/platform/..., /v1/schools/:schoolId/... and narrowly defined /v1/auth/... and /v1/webhooks/:provider paths. School routes remain membership-checked even when the ID is a UUID. Generate an OpenAPI contract and frontend client types; do not expose ORM row shapes directly.

  • Validate unknown fields, string lengths, date ranges, file limits and batch sizes; allowlist sort keys. Start with a maximum list size of 100 and adjust from measurements.
  • Cursor pagination with a deterministic tie-breaker for large lists. Support bounded page-number browsing if the school needs it; avoid unrestricted deep offsets and expensive exact counts on every request.
  • Return stable error codes with requestId. Use 401 for unauthenticated, 403 for forbidden action, 404 for unavailable or out-of-scope resources, 409 for stale versions/invalid transitions and 422 for validly parsed but invalid domain input.
  • Require an idempotency key for financial/provisioning commands and selected bulk operations. Scope by principal/tenant/operation; save payload hash and result. Reuse with different input is a conflict. Durable uniqueness rules outlive key expiry where duplication would be harmful.
  • Use expected version or If-Match for mutable aggregates. A stale edit does not silently overwrite a concurrent correction.
  • Async commands return 202 and a tenant-scoped job/status resource. Authorise job inspection and final artifact download separately.

7. Platform onboarding and commercial lifecycle

Store contract versions and accepted commercial terms as immutable snapshots: plan, subscription line items, separate maintenance recurrence, optional setup charge, effective dates, billing contacts and approved tax fields. Existing customer terms do not change when the plan catalogue is edited.

Use separate states for contract, subscription, tenant access, provisioning run and invoice/payment. “Invoice unpaid” is not automatically the same as “school suspended.” Define grace periods and read-only behaviour as an explicit product policy, with a controlled export/support route.

Provisioning is an idempotent state machine:

commercial terms recorded → tenant created → defaults seeded
→ first membership created → setup invitation queued → setup completed
→ activation conditions checked → active

Each step has a stable key and result. A failed email retries the invitation, not tenant creation. A consumed/expired setup link cannot be replayed. Activation is explicit and requires the accepted terms and administrator setup appropriate to that customer; payment gates are configurable commercial policy.

Subscription renewals use immutable invoice lines and unique billing-period keys so a worker retry cannot double bill. Maintenance and subscription recurrence produce distinct charge lines. Platform payments never allocate against a student's dues.

Support grants name the operator, school, reason, allowed actions/data, expiry and school approval evidence. Recheck before each sensitive action; audit reading private records and downloading exports. Platform administration is not blanket school impersonation.

8. Fees, payments and accounting

Pilot fee subledger

Support fee schedules, generated charges, concessions, authorised adjustments, cash/bank payment entry, payment allocations, numbered receipts, cancellation/reversal and balances. Prohibit deletion of posted receipts. Refunds and unapplied advances are explicit records. A correction preserves the original and issues a linked reversal/replacement.

Charge-run uniqueness includes tenant, enrolment, fee component and billing period. Receipt numbering uses a transaction-safe tenant/series counter; never use MAX(number) + 1. Define the policy for cancelled receipt numbers and preserve their history.

Payment, receipt, allocation, audit and outbox changes commit together. Allocation totals cannot exceed settled funds or charge balance. Serialize relevant balance changes with row locks in a consistent order, or use equivalent conditional writes with bounded retries. Balances derive from posted entries; cached totals are rebuildable.

First pilot can reconcile manually entered payment references. Online student payment collection comes in the next slice after merchant ownership, settlement destination and refund responsibilities are agreed with the pilot school. Keep payment-provider credentials and merchant mappings separate for your platform's revenue and each school's student payments; do not assume your merchant account can collect for every school.

Reliable provider processing

Verify the provider signature over the required raw payload; resolve the merchant/tenant from a trusted stored mapping. Persist a deduplicated inbox entry before acknowledging a valid callback. Process asynchronously with retries, an explicit state machine and reconciliation for missing/out-of-order events. A browser redirect never marks funds settled.

Uniqueness on provider/merchant/event and on the provider payment reference prevents duplicate receipts. If a callback lacks sufficient authoritative state, fetch provider status through its adapter. Unknown mappings or inconsistent amounts go to review. Test settlement followed by refund, duplicate and delayed events, and failure after inbox commit.

Full accounting in its own release

Implement school chart of accounts, balanced journals, receivables/payables, bank/cash, reconciliation, assets/depreciation where applicable, period closing, reversals and reports only after accountant-approved scenarios exist. Define tax and reporting mappings with the school's accountant; this plan does not determine statutory applicability.

Journal lines require one-sided nonnegative debit/credit amounts and valid same-tenant accounts. Posting must atomically validate total debits equal total credits, open period, source uniqueness and permissions. A controlled database posting procedure/trigger plus privileges must prevent direct insertion of an unbalanced posted journal; a cross-row CHECK alone cannot enforce the aggregate.

Lock the period and relevant document state during posting; period close and concurrent posting must follow the same lock protocol. Posted records are immutable and corrections reverse them under an approved policy. Operational source keys prevent duplicate posting from a retried business event.

Fees remain the receivables source of truth. When GL launches, choose a cutover date, reconcile opening balances and mark which historical records are represented in those balances; do not repost the same historical receipts. Separate operational fee reports from financial reports until reconciliation proves agreement.

9. Messaging, exams and record history

Communication

Store notice content versions per language, approval decisions and the audience definition. Approval freezes content and an eligible recipient snapshot. Audience preview returns recipient counts, channel availability and estimated units, without exposing parent contacts to other parents.

At delivery time, recheck current guardian relationship, channel permission, optional linked membership and cancellation so a revoked guardian is excluded. Parents can receive WhatsApp without a portal account; private records and action links still require authentication or a separately verified action flow. Do not silently expand an approved audience; additions or substantive content edits require a new approval. Preserve snapshot and exclusion reasons.

WhatsApp is the confirmed primary single/bulk channel for the pilot, through the official Business Platform directly or an approved provider. Recommend a school-owned sender identity, approved English/Hindi templates and per-school sending budgets. A single send is a one-recipient campaign; bulk sending fans out to private per-recipient deliveries. Track queued, submitted, provider-accepted, delivered, failed and read separately. Deduplicate identical approved content/destinations without assuming that a shared phone proves authority over all children. Apply sender/provider limits and permission checks in the worker.

Free and paid eligibility is evaluated per message, not by batch size. The same configured API handles eligible zero-Meta-fee service replies and chargeable messages. Keep pricing/allowance rules effective-dated, reserve estimated budget, and reconcile final provider billing. The WhatsApp free/paid comparison records current evidence, provider fees, trial restrictions and routing examples. Do not promise free bulk template broadcasts based on a service-message allowance.

Reading a notice does not complete consent, payment or homework. Those are separate domain actions with their own actor, timestamp and evidence. English/Hindi content versions remain distinct from each parent's UI language. AI translations stay drafts until staff approve them.

Exams

draft → submitted → changes_requested → resubmitted → approved → locked → released

Approval is bound to a paper version and checksum. Editing approved content creates a new version and invalidates approval. Paper access uses dedicated permissions and private files, not normal teacher attachment access; answer-key access is separately controlled. Author, reviewer, approver, releaser and invigilator are separate recorded responsibilities.

Store scheduled exam sessions, invigilator assignments, student eligibility and attempts/absence. Mark entries retain revision number, actor, time and correction reason; validate maximum marks and authorised subject/section. Use optimistic versions for competing entry/correction.

Report publication freezes the source mark revisions, grading policy version, calculation rules and generated artifact. Publish only authorised student-visible fields. Corrections create a superseding publication; parents see the current published version while authorised history remains. Never regenerate a historical report silently from today's marks.

Audit is not a substitute for domain history: paper reviews, attendance revisions, marks revisions, receipt reversals and publication versions have first-class records. The application role can append audit rows but cannot update/delete them. Export audit evidence off-host with restricted access; this improves tamper resistance but does not make a database administrator technically incapable of tampering.

10. Library, inventory and procurement

Share vendors, locations, approval infrastructure and acquisition references. Keep the ledgers distinct:

  • Consumables use append-only quantity movements and consistent units; on-hand is derived or a reconciled projection. Prevent negative stock through row locks/conditional balance updates in the same transaction.
  • Assets track individual tags, custody intervals, location, condition and maintenance. Custody is not an accounting disposal.
  • Library separates title/edition metadata from physical copies. Accession/barcode uniqueness is per school. Use a partial unique index on (tenant_id, copy_id) for open loans, plus copy/loan state checks. Concurrent borrowers cannot both obtain one copy.

Borrowing affects availability and custody, not ownership or GL. Returns are idempotent and preserve condition/overdue history. Lost, damaged and withdrawn copies use explicit policies and approved write-offs; scanning a withdrawn copy cannot restore it automatically.

Procurement records requested, ordered, received, accepted, rejected, billed and returned quantities separately. Lock outstanding order quantities during receipt acceptance to prevent over-receipt beyond approved tolerances. Partial receipt leaves the remainder open. Unique source references prevent duplicate accession/stock updates from retries.

Supplier invoice matching compares approved order, accepted receipt and supplier bill. Exceptions require a decision, not automatic changes to the original order. School accounting determines whether a receipt accrual or other posting is appropriate. Donations and opening registers are explicit sources and do not manufacture supplier invoices.

Separate request, approval, receipt, invoice posting and payment permissions; permit documented combined roles for small schools while retaining evidence. Closing procurement exceptions and validating accountant reports is a release gate for this module.

11. Private files, galleries and downloads

All files use private S3 keys generated by the server under tenant/object namespaces; the namespace is organisational, not an access check. Metadata includes tenant, owner record, uploader, size, content type, checksum, scan state and retention class. Keep unreleased exam files in a stricter permission category than general attachments.

Create a size/type-limited upload intent, then a short-lived upload authorisation. Confirm the uploaded object's real size/type/checksum server-side and quarantine it until required scanning/validation succeeds. Use immutable random keys or pinned object versions so a reused upload URL cannot replace content after validation. Only approved objects become attachable/publishable.

Gallery flow: upload → review media and audience → publish a gallery version → build package → grant access → notify → authenticate/recheck access → issue short-lived download URL. Package identity includes gallery/content version, audience policy and variant. Reuse a ZIP only when all authorised recipients have access to exactly its contents; narrower audiences need filtered packages.

An application grant is revocable and expiring. Redeeming requires the current guardian relationship and gallery permission. The signed S3 URL is a bearer capability usable until expiry under its storage rules; revoking the application grant blocks future issuance but does not recall downloaded files or necessarily invalidate an already-issued URL. Keep URL lifetimes short and logs free of signatures. S3 presigned URL behaviour.

ZIP generation streams in bounded jobs with file/count/total-byte limits, safe filenames and cleanup of failures. Separate original retention from package retention. Deletion is an audited workflow across metadata, objects, derived packages and the documented backup-retention window.

12. Jobs, consistency and integration contracts

Use a transactional outbox from the first release:

  1. Commit the domain mutation, audit record and outbox event in one database transaction.
  2. A relay claims outbox rows and enqueues pg-boss work with stable event identifiers.
  3. A worker processes with a fresh trusted tenant context, source/version checks and a durable deduplication key.
  4. Record success, retryable failure or terminal failure with an operator-visible reason.

A relay may crash between enqueue and marking the outbox dispatched, so consumers must tolerate duplicate delivery. pg-boss queue guarantees do not make external payments, emails or object writes exactly-once. If a provider offers no idempotency support, a crash after provider acceptance can leave an ambiguous send; reconcile when possible and document any residual duplicate risk. pg-boss documentation.

Initial events: TenantProvisioningRequested, AdminSetupRequested, AttendanceFinalised, HomeworkPublished, FeePaymentRecorded, NoticeApproved, ReportPublicationRequested, GalleryPackageRequested and UsageReservationCreated. Version event schemas. Payloads contain minimal IDs/version/context references, not unnecessary child data.

Workers are bounded by tenant and workload. Separate delivery, reports/imports and media queues. Heavy jobs checkpoint chunks, obey timeouts, use exponential retry/jitter for transient failures and expose exhausted retries. Cancelling a scheduled message or revoking a gallery must be rechecked before an external side effect.

Adapter ports include mail/message send/status, payment create/query/refund, object storage and AI generation/usage. A fake adapter supports development; provider contract tests run in a sandbox before launch. Store credentials in secrets configuration or encrypted credential storage with keys outside PostgreSQL, never in general tenant settings JSON.

13. Deployment, cost and recovery

Pilot deployment: one modest host running reverse proxy, API, worker and PostgreSQL as separately restartable services; private external object storage; encrypted off-host backups; a small staging environment using synthetic data. Constrain worker memory/CPU so ZIP or PDF work cannot starve the database. Keep PostgreSQL private and expose only the intended TLS entry point.

Run migrations as a one-off deployment job, not in every API replica. Use reviewed expand/backfill/contract changes, a migration lock, tested backups and a forward-fix or rollback runbook. Pin container/dependency versions. A failed worker should not take the API down.

Start with a database connection budget, for example API 10 + worker 5 + relay/queue allowance + reserved operational connections, then measure. Count separate pg-boss pools and every future replica; do not multiply default pools accidentally. Bound request/statement timeouts and long exports.

Measure API latency/error rates, slow queries, pool waits, locks/deadlocks, queue age, exhausted jobs, oldest outbox event, webhook reconciliation failures, disk/WAL growth, backup age and restoration outcomes. Include tenant and request/job IDs in structured logs while redacting contacts, credentials, raw child records and signed URLs.

Recovery policy: nightly encrypted off-host backups are the minimum for synthetic/internal trials; they permit up to roughly a day's data loss. For live fees and daily records, target RPO ≤15 minutes using continuous WAL/PITR or a managed equivalent, with a proposed RTO ≤4 hours. These are targets until a timed restore proves them. If cost cannot support the agreed recovery policy, resolve that before live launch. Restore database, encryption keys and referenced S3 versions coherently; validate recovery with a school reconciliation report.

Restore to an isolated environment and prove all tenant rows were included, not silently filtered by RLS. Test school export/recovery separately from whole-database disaster recovery. Offboarding should revoke access, stop scheduled work, provide an authorised export and follow the agreed retention policy; cancellation does not immediately delete historical evidence.

Meter active students/entitlements, stored bytes, downloads, delivery units, imports/report workload and AI spend. Reserve quota atomically before expensive jobs. Apply soft alerts and explicit hard limits by plan. Separate billing usage from operational telemetry.

Scale in response to measured constraints: reduce query cost and tune indexes first; move heavy workers to another host when contention appears; move/improve the database for memory, I/O or availability; add API replicas for sustained API saturation. Introduce Redis or separate services only when a documented bottleneck or coordination requirement warrants them. This design carries no unmeasured students-per-server promise.

14. AI extension contract

AI begins after teaching, timetable, resources and parent relationships are dependable. Feed only authorised minimal source records into each request. Source documents and student submissions are untrusted content and cannot grant tool access or broaden the query scope.

Store request type, tenant, actor, source record/version references, provider/model configuration, prompt-template version, estimated/reserved cost, actual usage, generated draft, review decision and published version. Cap per-request, per-school and platform spending; release unused reservations safely after failure.

Start with class-level syllabus drafts, reviewed translations and catch-up packs from lessons actually taught. AI output is a proposed document, never the authority for attendance, marks, fee balance, permissions or posted journals. No student-facing autonomous agent is included in the pilot. Validate provider data handling and school consent/privacy requirements before sending child-related data externally.

15. Delivery sequence and acceptance gates

The ranges below are planning estimates for one experienced backend developer, with school feedback, frontend work and provider approvals requiring additional time. They are not calendar commitments. Re-estimate after the foundation spike and the first end-to-end workflow.

Phase A — Foundation, approximately 3–5 developer-weeks. Repository, CI, API/worker bootstrap, migrations, identity/session integration, tenant RLS wrapper, permissions, platform contracts/provisioning, outbox, audit and backup/restore runbook. Exit: two synthetic schools provision independently; setup/recovery is secure; cross-school requests, job execution and connection reuse tests pass.

Phase B — Daily academics, approximately 4–6 developer-weeks. Academic years/sections/subjects, student/guardian import, enrolments/placements, scoped teacher assignment, attendance corrections, homework/submissions and basic parent endpoints. Exit: a school completes a representative week and year-transition rehearsal; unrelated guardians and teachers cannot retrieve protected records or fields.

Phase C — Fees and pilot readiness, approximately 3–5 developer-weeks before re-estimation for WhatsApp onboarding. Fee subledger, manual payment reconciliation, receipts/reversals, WhatsApp single/bulk notices, approved template languages, opt-in/out, delivery callbacks, per-school budgets, operational quotas, exports, load testing and timed restoration. Exit: accountant reconciles sample balances/receipts; duplicate/concurrent writes are safe; sender onboarding/templates and billing reconciliation pass; school signs off the agreed workflows and recovery policy. Provider approval time is external to developer effort.

Phase D — Communication and assessment, approximately 4–7 developer-weeks. Richer audience automations, Hindi/English publishing workflows, optional online payments, exam paper review/release, marks and immutable report publication. Exit: audience revocation, delivery reconciliation and historical-report corrections pass acceptance scenarios. Core WhatsApp single/bulk delivery is included in the pilot phase above.

Phase E — Resources and finance, separately estimated after accountant discovery. Library/circulation → inventory/assets → procurement → full accounting and cutover. These can ship as separate increments; “full accounting” is not a small extension to receipts. Exit: concurrency tests, receipt/invoice matching, balanced postings, period-close races and accountant-approved reports pass.

Phase F — Events, then AI, separately estimated. Private galleries, audience-filtered ZIPs, expiring grants and retention; then reviewed AI drafts with usage caps. Exit: real audience/download/retention scenarios and external-provider data policies are validated.

Phases A–C imply approximately 10–16 backend developer-weeks before contingency, rather than a promise of a production pilot in a few weekends. Full scope is a substantially larger programme. A narrow internal trial can happen earlier using synthetic data; live school use needs the relevant release gates.

16. Verification plan

Use unit tests for meaningful transition/calculation rules; integration tests against real PostgreSQL for constraints, RLS, transactions and posting; HTTP tests for guards/DTOs; concurrency tests for shared balances/copies; adapter sandbox tests; and a timed restore drill. Run security tests under the actual restricted runtime roles, not a test superuser. Frontend demos and mocked repositories cannot prove these properties.

Required release scenarios:

  1. School A cannot read/write School B records through IDs, filters, counts, imports, exports, job status, files or support routes. A composite FK rejects a cross-school child relationship.
  2. Missing tenant context denies access; pooled connection reuse across alternating schools and rolled-back requests leaks no context. Worker retries obey the same rule.
  3. A same-school unrelated parent cannot read a child profile, report, fees or gallery. An unassigned teacher cannot read restricted paper/subject records or change attendance.
  4. Setup/reset token expiry, atomic single-use consumption, restricted temporary-password sessions, membership revocation and support-grant expiry work across concurrent requests.
  5. Attendance batch replay and competing corrections preserve one current state plus history. Academic-year rollover and section transfers do not erase records or widen historical access.
  6. A duplicate charge run, payment request, provider event or renewal job produces one economic result. Out-of-order payment/refund events reconcile correctly.
  7. Competing payment allocations cannot over-allocate; refunds cannot exceed available refundable funds; simultaneous receipt issuance cannot duplicate numbers.
  8. Unbalanced journal posting, duplicate source posting, closed-period writes and close/post races are rejected. Reversals preserve original evidence.
  9. Two concurrent loans of one copy yield one successful loan; competing stock issues cannot make on-hand negative. Retried goods receipts do not duplicate stock/copies.
  10. Editing an approved paper or message invalidates approval; cancelled schedules and revoked guardians are excluded at execution. Corrected reports create a superseding publication.
  11. A crash after domain commit but before enqueue loses no work. A crash after an external side effect is reconciled or produces an explicit ambiguous state, with no claim of impossible exactly-once delivery.
  12. Private/unscanned uploads remain inaccessible; package contents match every recipient's audience. Expired/revoked grants block new URLs; retention cleans only intended objects.
  13. A fresh environment can restore backups within measured recovery targets; reconcile student counts, latest fee entries, audit evidence and referenced files.

Load-test the pilot school's actual dataset size and peak mix: morning attendance submissions, parent dashboard reads, fee queries, exports and one concurrent heavy job. Record p95/p99 latency, error rate, memory, pool waits and queue age; agree acceptance thresholds before launch. No capacity or latency claim is established by this plan.

17. First implementation backlog

Execute these as reviewable vertical slices, each with its migration, service, API contract and relevant verification:

  1. Bootstrap API/worker, configuration validation, health/readiness, CI, PostgreSQL and version-pinned dependencies.
  2. Implement restricted database roles, one tenant-scoped table, composite foreign keys and the transaction helper; prove two-school isolation before multiplying tables.
  3. Implement sessions, setup/reset, membership selection, permission scopes and initial platform-admin MFA.
  4. Implement immutable commercial terms, idempotent tenant provisioning and first-admin setup with an outbox-backed invitation.
  5. Implement audit append privileges, inbox/outbox relay, retry/status tools and the first restore rehearsal.
  6. Implement academic year, section, subject and teacher assignments; seed synthetic school scenarios.
  7. Implement staged student import, enrolment, placement and verified guardian linking; expose permission-filtered student profiles.
  8. Implement attendance with revisions and concurrency handling; run a teacher-to-parent end-to-end flow.
  9. Implement homework audience/submission/feedback, bilingual notice approval, WhatsApp sender/template setup, single/bulk delivery, opt-out, cost classification and callbacks.
  10. Implement fee schedules, charge runs, manual payments, allocations, receipt/reversal and accountant reconciliation; then perform the pilot release review.

The first demonstrable backend result should be: platform admin provisions two schools → school admin sets up their account → assigns a teacher → enrols a student → verifies a guardian → teacher records attendance → that guardian sees the permitted record → the second school cannot access it → the data can be restored.

18. Decisions to close during implementation discovery

These are business inputs, not blockers to writing the foundation:

  • Pilot school count, student count, simultaneous staff/parent usage, import sources and acceptable downtime/data loss.
  • Exact fee rules, receipt series, concessions, advances, refunds, payment merchant/settlement ownership and accountant-approved accounting/report requirements.
  • Guardian verification evidence, custody/restriction handling, historical teacher access and parent/student account recovery.
  • Subscription suspension/grace/export policy; precise plan limits, setup and maintenance recurrence; who approves support access.
  • Message channels/providers and delivery cost limits; media consent/audiences, file limits, retention and export expectations.
  • Applicable child-data, consent, tax and contract requirements reviewed against current rules with the relevant qualified advisers before live operation.

Default implementation can proceed with manual school payment recording, session authentication, WhatsApp sandbox/synthetic callback testing, no live AI, private attachments and synthetic school data while sender onboarding and commercial choices are resolved. Live WhatsApp requires the approved school sender, valid messaging permission, templates where required and a configured budget.
