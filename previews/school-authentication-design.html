Library decision

Selected: NestJS Passport integration with the local strategy, node-argon2 for Argon2id, and Fastify cookie transport. The API will use random opaque sessions whose hashes are stored in PostgreSQL. The application owns the school-specific permission checks and token lifecycle; Passport does not supply those rules automatically.

The established strategy interface fits the existing school-code plus school-scoped username model and keeps the reviewed database schema authoritative. A full auth framework's schema/adapter conventions would need extra adaptation to the protected global identity tables and school login identifiers. The newer Nest authentication package is deferred while its lifecycle and adapter surface are evaluated separately.

Passport 0.7/local 1, Nest Passport 12 and node-argon2 0.45.1 were inspected during design. Exact installed versions and audit results will be recorded in the backend lockfile and implementation evidence.

Current implementation state

F01 is merged. F02 library selection and the SQL/lifecycle design are approved for implementation. The controls below are requirements; implementation and test evidence will be recorded separately before review. No real invitations or recovery messages have been sent.

Identity before tenant context

Authenticate

Resolve the school and username through a narrow reviewed database interface. Verify the password using Argon2id and reject inactive identities and schools without revealing which identifier was wrong.

Authorize

Read the current session, user status and active school membership. Resolve allowed actions and the requested resource from server-owned data; a supplied school or membership ID is only a selector.

Isolate

Begin on one checked-out connection, validate and lock current authorization state before setting tenant context, then perform the authorized tenant query in that same transaction. Keep same-school foreign keys and forced row security for domain data.

The runtime retains no direct global credential/session table grants. A dedicated school_auth role is NOLOGIN, NOINHERIT and NOBYPASSRLS, owns no tables, and is never granted to the runtime. Targeted policies apply only to this role, with explicit column/operation grants for its named functions. Forced RLS stays enabled. A privileged, idempotent role-provisioning step is required before the migration; production operators must perform its equivalent separately.

The migrator receives SET permission with INHERIT FALSE to assign named function ownership. Schema CREATE is temporary during ownership transfer and revoked afterward. Each SECURITY DEFINER function fixes its search path to pg_catalog, pg_temp, fully qualifies relations, revokes PUBLIC execute and grants only named entrypoints to the runtime. Internal helpers are not runtime-executable. This makes pre-auth school-code lookup possible without making a browser-supplied tenant trusted.

Lifecycle requirements

Individual invitations

An operator-only CLI issues first-admin invitations for an existing school; public school provisioning remains F04. Invitation tokens expire, are stored hashed and are consumed atomically once. New owner contacts become verified only after the intended user proves possession through acceptance. A first-admin setup flow establishes a pending person's password only under its intended setup conditions. An invitation for an existing active global user must require that user's own authenticated acceptance and must never let a school administrator replace the user's global password.

Sessions and school switching

Use 32 random bytes for the bearer token and store its SHA-256 hash. Production uses __Host-campus_session with Secure, HttpOnly, SameSite=Lax, Path=/ and no Domain; insecure cookies require an explicit loopback-only development flag and are forbidden in production. Apply an eight-hour absolute and thirty-minute idle expiry. Recheck user/security and membership/permission versions, revoke stale sessions and rotate on school changes.

Derive a CSRF value from the high-entropy raw session token using HMAC-SHA256 and a fixed domain separator; persist only its hash. Return it only in authenticated no-store JSON. Cookie-authenticated mutations require exact configured Origin and the CSRF header. Pre-auth JSON mutations also require exact Origin and a custom request header. Never log bearer, invitation or recovery tokens. Login finalization rechecks the observed verifier and versions under locks to prevent recovery/login races.

Recovery

Recover through an already verified owner channel; callers cannot supply a destination. Store purpose-bound action tokens hashed with expiry, target, consumed timestamp and security-version snapshot. Consumption locks token/user state, changes the password once, advances the security version, revokes prior sessions and invalidates outstanding recovery tokens. Recovery does not sign the user in automatically.

Test transport is injectable. An unconfigured delivery adapter returns the same service-unavailable result before any account lookup or token issuance, rather than implying that instructions were sent. A protected, explicit development file outbox may write private mode-0600 delivery material outside tracked files. No real delivery provider is enabled in this slice.

Browser and abuse controls

Check the configured origin and CSRF protection for unsafe requests, including login and token acceptance. Passwords require at least 15 Unicode code points without MFA, allow spaces/Unicode, and are bounded at 128 code points and 512 UTF-8 bytes, without composition rules. Use explicit Argon2id parameters (64 MiB, 3 iterations, parallelism 1), a same-cost dummy verifier and a bounded concurrency limit of 2; benchmark these project choices. Bound input and single-process IP/account limiter maps; coalesce session activity writes instead of writing raw per-request traffic logs. Full shared rate limits and traffic telemetry remain F03; necessary auth protections cannot wait for that module.

Resource scope in this slice

Enforce own-school, own-identity and membership-management resources available in IAM. Teacher/class and guardian/child scopes require their domain records in later issues; F02 must not claim those checks are implemented early.

Required verification before review

  • Same username across two schools resolves the correct membership; wrong-school and unrelated identity access fail.
  • Unknown and wrong credentials share the same public failure shape; missing or unconfigured delivery does not leak tokens or claim delivery.
  • Single-use invitations and recovery survive replay, expiry and concurrent consumption tests.
  • Existing-user invitations cannot reset a global password or take over another membership.
  • Revocation, suspension, expiry and school switching invalidate stale context and sessions.
  • Unsafe requests reject missing/invalid CSRF and untrusted origins; cookie protections are asserted.
  • The runtime cannot read/write global identity tables directly or change ownership/RLS; functions cannot be shadowed through search paths.
  • F01 regression checks, a fresh database migration, migration reruns and CI pass.
