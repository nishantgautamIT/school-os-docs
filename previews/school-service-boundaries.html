Current decision

F02 is deferred. Its tested implementation is preserved in draft backend PR #2; it is not merged. When resumed, the identity implementation belongs in tenant-user-service. F04 is next. Full F03 traffic/telemetry work is also deferred.

The new identity-service repository and remote authentication protocol have not been created or implemented by this design. Existing foundation tables and database roles have not yet been extracted or renamed.

Two clear owners

tenant-user-service

  • Global user identity and verified owner contacts.
  • Passwords, login, MFA when introduced, sessions, logout and revocation.
  • Invitations, recovery and school membership acceptance.
  • Membership status, roles, permission grants and their versions.
  • Identity-related audit events, account normalization rules and local password-work bounds; common ingress enforces HTTP attempt policies.

campus-core-api

  • School profile, tenant business lifecycle, onboarding orchestration and subscription workflows.
  • Public school website drafts, revisions, publishing and private enquiries.
  • Students, guardians, staff assignments, academics and attendance.
  • Homework, exams, reports, fees, receipts and messaging workflows.
  • Business resource access checks, domain audit and business-operation quotas; common ingress enforces HTTP request limits.

The core defines what actions mean for each domain. Identity stores who receives those grants. A granted action never bypasses a domain rule: for example, a report must be published before a parent may read it.

Every protected request checks both boundaries

  1. Identity verifies the session and selected school membership, including current status and permission state.
  2. The core receives a trusted identity context through a reviewed internal contract. Browser-supplied user, role and tenant headers are not trusted.
  3. The core checks the requested action and the actual resource relationships: school ownership, teacher-to-class assignment, guardian-to-child link or publication state.
  4. The core starts its scoped domain transaction with the verified tenant and applies forced row security and same-tenant keys.

Example: identity may establish that a user has the parent role in school A. The core must still prove that student X is that parent's linked child in school A before returning attendance. The identity service does not query student tables to make this decision.

Keep user/session/tenant/membership IDs, permission versions and freshness requirements explicit in the service contract. Do not trust a role name alone. Protected operations fail closed when the required identity decision cannot be obtained or verified.

Physical separation changes the transaction model

The deferred F02 draft validates identity under locks on the same PostgreSQL connection as the domain query. Two independent services cannot preserve that single transaction across an HTTP call. Extraction must therefore define authorization freshness, revocation behavior, timeouts and outage handling before protected domain APIs are enabled.

The first protocol candidate is authenticated internal introspection of the existing opaque session, followed by core resource checks. This is a proposal, not an implemented endpoint. If signed short-lived access tokens are selected instead, the core must validate issuer, audience, signature and expiry, and the design must state how long revoked access can remain usable. Local signature validation alone does not guarantee immediate revocation.

See OWASP authorization guidance and microservices security guidance.

One common rate-limiting layer

General HTTP rate limits belong in the mandatory gateway/common ingress component. Keep one limiter implementation and one policy configuration for both APIs. The gateway checks the applicable policy and routes to the destination service. It does not call every service, and the core does not call identity just to count requests.

Common policies

IP/route bursts, account-targeted login/recovery policies, public site/enquiry submission limits, and verified user/tenant request budgets. Take account-normalization rules from the identity contract and tenant identity from a trusted validated context; a browser-supplied tenant header is never a quota identity.

Common counters

Use bounded in-memory counters for one gateway process initially, and atomic namespaced Redis counters before multiple gateway replicas. The shared counter store does not require a separate HTTP rate-limit service. Keep raw request counters outside PostgreSQL.

Domain rules stay in core

WhatsApp recipient/spending reservations, export job concurrency, usage entitlements and idempotency depend on business state. They remain core workflow rules. Password-hash concurrency and database-pool bounds also remain local resource protections; neither requires a second copy of the generic HTTP limiter.

Rate-limit examples: login → gateway account/IP policy → tenant-user-service; enquiry → gateway site/IP policy → campus-core-api. This describes rate limiting only; authentication still follows its reviewed identity contract.

Backends must have private/restricted ingress so public clients cannot bypass the gateway. Deploy the common policy enforcement before removing any existing defensive limiters. F04 must include the shared enquiry policy even while full F03 traffic/telemetry is deferred. This is the target design; no gateway or Redis deployment is claimed here.

School creation is a core workflow

The core owns school details and the draft website. It requests the first administrator's identity/membership setup from the identity service using an idempotent operation ID. Identity owns verification, invitation acceptance and password creation; a matching email alone never attaches an existing account.

Once services are separate, school creation and owner setup are not one cross-service SQL transaction. Track pending and failed setup explicitly and make retries safe; use an outbox/inbox or another reviewed durable delivery mechanism at integration time. The core must not report owner activation merely because it queued an invitation request.

Platform support also receives no automatic right to private school records. Any future support-data interface needs a verified support identity and an explicit scoped, expiring grant. Administrative database provisioning is a separate operator tool, not a support portal.

Database ownership follows service ownership

tenant-user-service owns identity tables and their migration lifecycle. campus-core-api owns school and domain records, including public projections and enquiries. Use separate database credentials and explicit grants; the core must not read password hashes, refresh/session secrets or recovery tokens.

A single PostgreSQL installation may host the initial services, but that does not authorize unrestricted cross-service table writes. The F01 legacy schema contains both control and IAM groundwork. Its migration history is retained; extraction needs a forward migration plan that preserves IDs and existing local data. If separate databases are introduced, cross-database foreign keys must become explicit contract/integrity checks.

The current core runtime still has F01 IAM membership/role grants. Revoking or replacing those is part of the future extraction migration; this document does not claim that privilege separation is already deployed.

Delivery order now

  1. F01: merged foundation.
  2. F04: next core slice: idempotent operator provisioning, structured website drafts, published-only pages and private enquiry storage with routing, validation and bounded abuse controls.
  3. F02: deferred; extract preserved auth work into tenant-user-service, review the service contract and integrate school-admin access.
  4. F03: deferred full traffic and telemetry module; shared counter support is required before multiple API replicas.

Until identity integration exists, setup/publishing uses protected operator tools. School-admin editing, private enquiry APIs, owner invitation delivery/activation and support-data APIs stay disabled. F04 remains integration-pending rather than being marked fully complete without those authenticated workflows. Public pages read only the explicit published snapshot; enquiries never become public page data.

F04 development must use a separate isolated database from the locally migrated F02 database, and a branch based on merged F01. Do not erase the F02 local volume, rewrite applied migrations or merge deferred auth into the core to satisfy a temporary dependency.
