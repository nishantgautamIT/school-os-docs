Four focused application services

tenant-user-service

Global identities, verified owner contacts, login/passwords, sessions, invitations/recovery, identity tenant directory, memberships, roles and permission grants. Extracted code and 30 local/fresh checks exist on a draft review branch. No core profiles, fees, student workflows or public websites.

campus-core-api

School business profiles and onboarding orchestration; future students, guardians, staff, academics, attendance, homework and exams. The first slice atomically provisions a pending school profile and outbox event. Its active database has no IAM schema.

campus-operations-api

Fees, receipts, school payments, platform subscription billing, accounting, inventory, library and procurement. School fee money and platform revenue retain separate ledgers/modules. Repository scaffold only.

campus-engagement-api

Public website drafts/revisions/publication, admission enquiries, notices, WhatsApp and notifications. Public content and private enquiries remain separate. Repository scaffold only.

campus-api-gateway is the shared ingress/routing/rate-limiting component outside the four application-service count. It is a scaffold, not an enforced deployment. Each domain service validates access to the resources it owns; core is not a proxy for all other services.

Keep technical API/event contracts small and versioned. Avoid shared business ORM entities and direct cross-service table writes. Heavy report generation, imports and bulk delivery belong in bounded worker processes owned by their domain service. Those workers have not been implemented by this slice.

Identity plus domain resource authorization

  1. Identity verifies the session and selected school membership, including current status and permission state.
  2. The destination domain service receives a trusted identity context through a reviewed internal contract. Browser-supplied user, role and tenant headers are not trusted.
  3. The destination service checks the requested action and the actual resource relationships: school ownership, teacher-to-class assignment, guardian-to-child link or publication state.
  4. The destination service starts its scoped domain transaction with the verified tenant and applies forced row security and same-tenant keys.

Example: identity may establish that a user has the parent role in school A. The core must still prove that student X is that parent's linked child in school A before returning attendance. The identity service does not query student tables to make this decision.

Keep user/session/tenant/membership IDs, permission versions and freshness requirements explicit in the service contract. Do not trust a role name alone. Protected operations fail closed when the required identity decision cannot be obtained or verified.

Physical separation changes the transaction model

The deferred F02 draft validates identity under locks on the same PostgreSQL connection as the domain query. Two independent services cannot preserve that single transaction across an HTTP call. Extraction must therefore define authorization freshness, revocation behavior, timeouts and outage handling before protected domain APIs are enabled.

The first protocol candidate is authenticated internal introspection of the existing opaque session, followed by core resource checks. This is a proposal, not an implemented endpoint. If signed short-lived access tokens are selected instead, the core must validate issuer, audience, signature and expiry, and the design must state how long revoked access can remain usable. Local signature validation alone does not guarantee immediate revocation.

See OWASP authorization guidance and microservices security guidance.

One common rate-limiting layer

General HTTP rate limits belong in the mandatory gateway/common ingress component. Keep one limiter implementation and one policy configuration for the application APIs. The gateway checks the applicable policy and routes to the destination service. It does not call every service, and the core does not call identity just to count requests.

Common policies

IP/route bursts, account-targeted login/recovery policies, public site/enquiry submission limits, and verified user/tenant request budgets. Take account-normalization rules from the identity contract and tenant identity from a trusted validated context; a browser-supplied tenant header is never a quota identity.

Common counters

Use bounded in-memory counters for one gateway process initially, and atomic namespaced Redis counters before multiple gateway replicas. The shared counter store does not require a separate HTTP rate-limit service. Keep raw request counters outside PostgreSQL.

Domain quotas stay with their owner

WhatsApp recipient/spending reservations, export job concurrency, usage entitlements and idempotency depend on business state. They remain workflows in operations, engagement or core according to the resource they affect. Password-hash concurrency and database-pool bounds also remain local resource protections; neither requires a second copy of the generic HTTP limiter.

Rate-limit examples: login → gateway account/IP policy → tenant-user-service; enquiry → gateway site/IP policy → campus-engagement-api. This describes rate limiting only; authentication still follows its reviewed identity contract.

Backends must have private/restricted ingress so public clients cannot bypass the gateway. Deploy the common policy enforcement before removing any existing defensive limiters. F04 must include the shared enquiry policy even while full F03 traffic/telemetry is deferred. This is the target design; no gateway or Redis deployment is claimed here.

F04 crosses explicit service boundaries

Core owns the school business profile. Its operator command records a reserved external tenant UUID with identity_link_state=pending; it does not claim that the identity registry or owner is active. The same transaction stores school.profile_provisioned.v1, an audit event and the idempotent result.

Engagement will consume the approved profile seed idempotently to create its own website draft. It will own publishing, enquiries and public routes. Identity will own owner verification and first-admin membership activation. Neither consumer/dispatcher nor the remote auth contract is implemented yet. A queued event is not a delivered or published result.

Cross-service setup needs explicit pending/failure states, retries and event/command deduplication rather than a single SQL transaction. Protected operator tools are used while identity integration is deferred. Private admin/enquiry/support APIs remain disabled. Full F04 remains open.

Data stays with its owner

Core owns business profiles, core audit and its provisioning ledger/outbox. Identity owns IAM and its tenant directory. Engagement will own public projections/private enquiries; operations will own its financial/resource records. Separate credentials and service-owned migrations prevent cross-service writes.

Core's new guarded migration removes unused legacy IAM tables only from an empty F01 database. It refuses application rows/custom identity permissions and rolls back rather than discarding data. The original F01 checksum remains unchanged. The preserved F02 database at55432 is untouched; new core and identity containers/databases use55433 and55434 respectively.

The divergent core/identity migration streams must never be merged together. External actor/tenant references cross service boundaries through contracts; core does not retain an FK into another service's user table.
