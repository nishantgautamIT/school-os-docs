F06 · Design before implementation · 4 November 2026

Submission is evidence.
Completion is a reviewed decision.

Next core workflow after merged lessons and homework.

Four operator actions

  1. record_submission: homeworkId, homeworkVersion, enrolmentId, evidenceKind and evidenceText. Only a member of the published audience can submit. Create one aggregate per homework/enrollment and its first immutable attempt; state becomes submitted.
  2. resubmit_submission: submissionId, expectedVersion, current homeworkVersion, evidenceKind and evidenceText. Allowed from submitted or changes_requested. Append an attempt, preserve all previous evidence and reviews, reset state to submitted and clear the current review. Identical evidence against the same source revision is rejected.
  3. review_submission: submissionId, expectedVersion, teachingAssignmentId, decision and feedback. Only a submitted attempt can be reviewed. The current homework revision must match the attempt. Decision accepted sets completed; changes_requested asks for another attempt.
  4. correct_submission_review: the same review fields and expectedVersion. Allowed only while the current attempt remains reviewed. Append a review that explicitly supersedes the previous review; retain both decisions and feedback. Accepted requires the current homework revision. Changes_requested may reopen an older completed revision so the student can resubmit against a corrected prompt.

Every action includes tenantId, requestId, operatorRef and a reason. Evidence kinds are written_response and offline_work; evidenceText and feedback are nonempty, normalized text of at most 4000 characters. No arbitrary files or URLs are fetched. Offline work means an operator-recorded description, not verified proof of physical work.

Eligibility and review policy

Homework must remain published and the academic year active for new actions. The immutable publication audience is authoritative: later transfers, withdrawals or inactive student profiles do not silently remove an assigned learner. Late submissions are accepted, with the India receipt date and late flag computed from the database clock after the shared school lock. Clients cannot supply a submission timestamp or completion flag.

Reviewers need an active staff profile and active teaching assignment for the homework's original section and academic year. Capture the assignment version and staff ID. These checks validate domain eligibility; F02 account binding remains deferred, so a command's operator label is not proof of a teacher's authenticated identity.

Homework corrections do not rewrite historical attempts or completions. Every attempt pins the exact homework revision; completion applies to that revision. New acceptance of a stale revision is rejected. A cancellation freezes new submissions/reviews but preserves existing history. Reading a message or submitting evidence alone never completes homework.

Five tables in migration 0011

  • learning.submissions: one aggregate per captured audience member, current attempt number, submitted/changes_requested/completed state, current review pointer and optimistic version.
  • learning.submission_attempts: immutable evidence, exact homework revision, receipt date/time and late flag. Same-school foreign keys tie it to the aggregate and retained homework event version.
  • learning.submission_reviews: immutable decision/feedback, attempt reference, original homework scope and captured reviewer assignment/staff/version; optional same-attempt superseded-review reference.
  • learning.submission_events: before/after metadata snapshots, action, resulting version, operator, database role, request and reason. Evidence and feedback remain in the referenced immutable attempt/review rows.
  • learning.submission_commands: normalized digest and original metadata-only result for exact retries.

All tables force tenant RLS. Runtime and dispatcher receive no grants. Composite references prevent cross-school, cross-homework, cross-attempt and wrong-section reviewer links. Current attempt/review pointer foreign keys are deferred within a transaction so creation and pointer changes commit together.

Atomicity and privacy

Take the request lock and shared school row lock used by lessons, publication and enrollment lifecycle. Validate and commit evidence/review, aggregate state, version event, security audit and receipt atomically. Concurrent review/resubmission and homework correction/cancellation serialize; expected versions reject stale commands. Exact retries return their original result even after school/year closure.

The protected CLI reads a regular private file, rejects symlinks, bounds input to 64 KiB and limits database execution time. Output/receipts/events omit evidenceText and feedback. Full evidence remains private. No private HTTP route, parent portal, notification, grading scale or catch-up generation is introduced. Swagger continues to list implemented HTTP routes only.

Verification gates

Real PostgreSQL tests will cover exact retry, concurrency, audience membership, late receipts, transferred learners, source revisions, eligible reviewers, review correction chains, explicit completion, tenant isolation and role denial, composite references, cancellation/closure, late-write rollback and protected CLI output. Run targeted checks during implementation, then one full local suite and a fresh-database CI gate. Evidence will be appended when verified.
