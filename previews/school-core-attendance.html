Record attendance.

A bounded operator workflow built on active academic years and stable annual enrollment IDs.

First attendance workflow

Record a bounded batch for a school, active academic year, section and explicit school date. Each supplied enrollment receives an explicit present, absent, late or excused status. Missing students remain unmarked; omission never silently means absent. Start with same-day recording in Asia/Kolkata, with the date inside the academic year. Historical backfill needs a separate eligibility design and is not implied by the current roster.

Capture the enrollment and section used when the mark was recorded. A later transfer or withdrawal must not rewrite existing attendance. One record per school/enrollment/date prevents duplicate marks from different sections. Stable attendance IDs and expected versions support corrections.

Corrections and history

Corrections target an existing attendance ID, require the expected version and an explicit reason, and preserve date, student, enrollment, year and recorded section. The original mark and each correction retain actor reference, database role, previous/next status, request ID and timestamp. Corrections can reference existing records after a transfer or withdrawal while the year remains active; closed-year correction policy is later work.

Isolation and transactions

New private attendance records, version events and retry receipts live in campus-core-api. All tables force tenant RLS and same-school foreign keys. No identity-service database joins or external messages. One shared school lock serializes marking with enrollment transitions and year closure. Validate every row before committing the batch, with history/audit/receipt in the same transaction. Changed request reuse conflicts; exact retries return original results.

Scope and acceptance

Keep operator-only commands until verified teacher and guardian authorization is integrated. Do not grant portal access from a teaching assignment alone. Test mixed-validity batch rollback, duplicate dates, wrong-school/year/section records, stale edits, concurrent marking/corrections/closure, withdrawal/transfer history, missing context, restricted roles and private command files. No WhatsApp send, homework, learning-completion claim or parent notification is implied by an attendance mark.

Command and database contract

mark_attendance accepts academicYearId, sectionId, attendanceDate (YYYY-MM-DD) and 1–200 rows of enrolmentId/status. All rows must be unique, currently active in that section/year and belong to registered students. The date must equal the database clock's Asia/Kolkata date, checked after acquiring the school lock, and fall within the year. A batch with any invalid or already-marked row rejects entirely. Reordering identical rows does not change the normalized retry identity.

correct_attendance accepts attendanceId, expectedVersion and status. It changes only the status/version and requires a nonempty correction reason. A status that is already current rejects. Both commands require tenantId, requestId, operatorRef and reason. Use npm run attendance:record with a private regular JSON file, at most 64 KiB. Unknown fields reject.

Migration 0009 creates attendance.records, attendance.events and attendance.commands. Records capture the immutable enrollment, student, year, recorded section, enrollment version and date. A composite enrollment identity foreign key binds the stored student/year to the annual record; section is a historical same-year reference that survives later transfers. One record per tenant/enrollment/date and one history event per record/version. All three tables force tenant RLS, with no public runtime/dispatcher grants. Results omit names and admission codes but remain private school data. SQL administrators remain privileged.
