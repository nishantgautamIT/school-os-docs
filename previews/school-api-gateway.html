campus-api-gateway routes published school pages to campus-engagement-api. Core, identity and financial services do not receive these requests or duplicate this generic limiter.

First gateway slice

Allow GET/HEAD for the exact school-page paths already implemented by engagement: /schools/:slug and its fixed home/about/academics/events/contact pages. Expose gateway liveness and bounded upstream readiness checks. Reject other routes/methods and request bodies. No login, private data, internal event receiver or enquiry write is enabled yet.

Implementation decision before coding

Use Node24 HTTP/HTTPS primitives and TypeScript for a narrow fixed-route adapter, with no runtime framework, proxy dependency or database. There is one configured engagement origin, no client-supplied destination and no redirects. This is not an arbitrary forwarding proxy. Existing domain APIs keep the Nest/Fastify stack; the small gateway has no business ORM or user-auth logic.

Primary references: Node24 HTTP API and HTTPS API. Limits and policies below are project decisions and require production tuning.

Common budgets

  • One global token bucket: capacity600, refill10 requests/second.
  • Per socket-derived client network: capacity120, refill2/second, including rejected routes and health checks.
  • Per public school slug: capacity600, refill10/second.
  • Per client-network/school pair: capacity60, refill1/second.

All applicable buckets are checked atomically before debit. Denied requests return429 with Retry-After and do not reach engagement. Counters stay in bounded process memory, never PostgreSQL. At most20000 keyed buckets; inactive fully-refilled buckets expire after120 seconds, with bounded sweep frequency. If capacity is exhausted, new keys fail closed with503 rather than evicting active budgets.

Use the socket peer, normalize IPv4-mapped addresses and group IPv6 by /64. Ignore Forwarded/X-Forwarded-For, user, tenant and role headers. No trusted-proxy address extraction is implemented in this slice; behind a proxy its peer shares one budget until an explicit proxy-trust contract exists.

Safe forwarding boundary

Only reconstructed canonical paths go to the fixed engagement origin. Reject encoded/traversal/query/absolute-form paths and body-bearing requests; forward no browser headers, cookies, bearer tokens or identity assertions. Use fresh fixed Accept/Accept-Encoding/User-Agent headers. Preserve only approved HTML and the upstream CSP; force no-store, nosniff, no-referrer and frame restrictions. HEAD performs the same bounded upstream GET but suppresses the downstream body.

Only200 HTML is served,404 becomes a small gateway404, and redirects/malformed responses/server errors become sanitized502. Readiness returns a sanitized200/503 based on a bounded engagement readiness request. Never cache a page or forward conditional headers, so an engagement unpublish becomes404 on the next normal gateway read.

Bounded resources

At most16 concurrent upstream requests, a3-second deadline,128 KiB page limit,4 KiB readiness limit and8 KiB header limit. No response decompression or redirect following. Socket/request/idle limits bound slow clients and upstreams. Client disconnect aborts upstream work. Use HTTPS for configured remote origins; loopback HTTP is development-only. The gateway holds no database credentials, event keys or user session secrets.

Deployment limits remain explicit

This implementation supports exactly one gateway process and in-memory counters; startup rejects a declared replica count other than1 or an unsupported counter store. Independent processes cannot share limits. Implement atomic Redis counters before multiple replicas. Restrict backend ingress and put TLS in front of the gateway before production exposure; these network rules and a production deployment are not created by this code slice. Direct access to an exposed backend would bypass gateway budgets.

F03's full traffic/telemetry remains deferred. F04 enquiries require a future dedicated submission policy and protected storage/authorization before that route is opened. Domain spending quotas and local password/DB concurrency bounds remain with the owning services.

Verification gates

Real HTTP tests for route/method/input allowlists, spoofed headers, token budgets/refill/capacity/concurrency, one upstream call per admitted request, CSP/no-store/HEAD behavior, unpublish404, deadlines/oversized content/headers/encoding/redirects, sanitized failures, readiness and disconnect cleanup. CI must build and run all checks. No deployment, private-route access or distributed limiter is claimed.
