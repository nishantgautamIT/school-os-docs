Implementation status and authentication

Snapshot: 3 November 2026. The gateway and engagement contracts include admission enquiries from feature PRs gateway #2 and engagement #3. These feature PRs were merged on 3 November 2026 after their CI passed. This catalogue does not claim a production deployment.

  • Identity: uses an HttpOnly session cookie. Mutations require the configured Origin, X-Campus-Request: 1 and JSON content type. Session mutations also require X-CSRF-Token. A browser cannot spoof its Origin or manually set an HttpOnly cookie. Use the configured app origin and cookie jar for tests. The gateway does not currently route identity endpoints.
  • Public gateway: school pages and optional admission submissions. Enquiries require an idempotency UUID, exact configured Origin, adult declaration and contact consent. Neither private enquiry inbox data nor internal receivers are publicly routed.
  • Private receivers: event delivery uses port 3003; enquiry ingestion uses port 3004. Both require computed HMAC signatures over the exact body bytes, with separate keys. Their operation-level server addresses override the engagement website address.
  • Private identity/core integration: identity introspection uses a separate mTLS listener on port 3441; the school-profile read uses port 3442. Both require trusted client certificates with exact service URI identities. Core also requires the opaque session cookie and an online school.read decision. These private routes are not registered on public identity/core listeners. When configured, the gateway exposes GET /api/schools/{tenantId} and forwards the session over mTLS to core using the common limiter. Gateway login/session-switching and resource-specific teacher/parent APIs remain closed. OpenAPI 3.0 cannot encode mTLS natively; mandatory certificates appear in operation descriptions and x-mtls-required. Academic, attendance and learning workflows remain protected operator commands.
  • Operations: fee commands are in progress; there is no implemented HTTP server. Its OpenAPI paths is intentionally empty.
Keeping future APIs documented
  1. Update the service's docs/openapi.json in the same PR as any HTTP change, including request/response schemas, errors, auth, and retry behavior.
  2. Run node --test test/openapi.test.mjs. The four HTTP services also run it through their existing test/check commands. Nest routes are extracted from TypeScript decorators. Native Node listeners have reviewed route manifests and source fingerprints.
  3. When a fingerprint changes, review the contract and update docs/api-coverage.json. A fingerprint forces a review; it does not automatically infer business semantics. Add newly introduced HTTP validation/security dependencies to the source manifest.
  4. From school-os-docs with sibling checkouts, run npm ci, npm run build:apis -- --sync, npm run check:sources and npm run check:apis. Commit the updated catalogue. The checker detects missing/stale operations, unclassified native listeners and changed reviewed source.
  5. When operations introduces an HTTP listener, copy the guard/test pattern into that service and add its real routes before publishing. Its current uncommitted operator scaffold is not modified by this documentation change; central source checks confirm it has no HTTP endpoints.

The contracts are reviewed documentation, not automatic runtime request validators. Re-run API behavior tests after changing implementation; this guard complements those tests.
