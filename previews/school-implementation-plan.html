Database

PostgreSQL 18 in Docker; separate bootstrap, migration-owner and restricted runtime credentials. Random local passwords remain in ignored .env; the API loads a separate .env.runtime containing only its restricted connection.

Backend

Node 24, TypeScript, NestJS 12 and Fastify. Health and readiness endpoints. No authentication or school-data endpoint is exposed yet.

Identity tables are groundwork

The schema stores users, memberships, school usernames, roles, permissions, password hashes and session token hashes. Login, invitation, recovery, session cookies and action/resource guards are the next milestone. The API role cannot read global identity, credential or session tables. Tenant RLS is defense in depth; the server must verify membership before choosing tenant context.

What is actually migrated?

control.tenants; iam.users, password_credentials, memberships, school_login_identifiers, permissions, roles, role_permissions, membership_role_assignments, sessions; ops.security_events.

Tenant-owned tables force row security. All relationships between tenant-owned rows include tenant_id. The runtime can append security events but cannot edit or delete them. The migrator owns schema changes and is not used by the API.

Reviewed SQL migrations are authoritative for the implementation. The broader catalogue remains a design draft. Drizzle query helpers may be added when domain repositories are implemented; it is not installed in this first slice.

Run the project

Prerequisites: Docker with Compose, Node 24 and npm. Clone campus-core-api and run these from its repository root. Docker binds the database to 127.0.0.1:55432. The API defaults to 127.0.0.1:3000.

npm ci
npm run db:up
npm run db:migrate
npm run check
npm run test:fresh
node --env-file=.env.runtime dist/src/main.js

Then open http://127.0.0.1:3000/health/ready. npm run db:down stops containers and retains the named database volume. Never run development fixtures or bootstrap scripts against production. Existing volumes retain their original credentials; changing .env does not rotate database passwords.

Working rules

  • Small feature branches and pull requests; no direct default-branch publication.
  • Every module brings its own reviewed migration, action/resource permissions and isolation tests.
  • Forward-only migrations: an applied checksum must never change. Use a new migration for corrections.
  • One transaction, one checked-out connection and transaction-local tenant context. No browser-supplied tenant is trusted on its own.
  • Rate counters, raw traffic and request logs do not become high-volume primary-database writes.
  • Keep all new design deliverables as HTML. Commit lockfiles and placeholder .env.example; never commit credentials or real school data.
