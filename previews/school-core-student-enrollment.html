F05 · Student registration and enrollment planning · 2 November 2026

One student identity.
A separate plan for each year.

Build on merged academic setup. Protected operator commands register school-owned students and plan their section/roll assignments in draft academic years. Private portals, live enrollment and identity integration remain separate work.

Precise scope

A registration is a school-owned record, not a login account or admission eligibility decision. Names never silently merge identities. Planned enrollments reserve a section/roll in a draft year; they do not activate the year, mark attendance, charge fees, promote a child or prove guardian/teacher rights. No HTTP student routes, imports, cross-service identity references, bulk registration, DOB, contacts, health data or uploads are added. Only synthetic data belongs in repository fixtures.

Four new private tables

people.students

School/student UUIDs, immutable school admission number, private legal name, registered/inactive status, version and timestamps. Admission numbers normalize uppercase and are unique per school. Same names with different admission numbers remain distinct. Profile corrections preserve the original ID.

people.enrolments

One immutable annual identity per school/student/year, current section/roll plan, planned/cancelled state and version. Composite school/year/section references prevent wrong-school and wrong-year placement. Cancel/restore keep the annual ID; another year gets another annual row, with the same student ID.

people.enrolment_events

One append-only-in-the-command-interface change per enrollment version: creation, revision, cancellation and restoration. Previous/current section/roll/state snapshots, request ID, actor/database role and reason retain planning history. No names/admission numbers are copied into history.

people.student_commands

School-scoped request/hash receipt and redacted result for atomic retries. Exact normalized replay returns the original receipt; changed payload conflicts. Receipts and CLI output omit legal names/admission numbers, but still contain private identifiers and planning metadata.

All new tables force RLS for their owner. Public runtime/delivery roles receive no schema or table access. Forward migration0005 preserves existing migrations/data and adds a section/year unique key for a database-enforced same-year foreign key.

Protected command contract

Common fields: action, tenantId, requestId, operatorRef and reason. JSON file must be a private regular0600 file at most16KiB. OperatorRef is a supplied audit label, not a verified human identity. Codes/IDs/parent references are immutable; expected versions fence edits.

  • register_student: admissionNumber, legalName.
  • rename_student: studentId, expectedVersion, legalName. Names are stored only on the protected student record; the audit identifies the version change without duplicating names.
  • plan_enrolment: studentId, academicYearId, sectionId, rollNumber (nullable).
  • revise_plan: enrolmentId, expectedVersion, sectionId, rollNumber.
  • cancel_plan: enrolmentId, expectedVersion. Cancellation releases capacity and roll reservations, keeping the last plan/history.
  • restore_plan: enrolmentId, expectedVersion, sectionId, rollNumber. Only a cancelled plan can be restored.

Roll labels normalize uppercase; digit-only labels remove leading zeroes and must be positive, so01 and1 cannot reserve competing numeric rolls. Unspecified rolls use explicit null. Names remain Unicode. Unknown fields and invalid IDs, versions, labels or controls reject.

Capacity, year and transaction rules

  1. Require operator credentials, normalize/hash the request, lock its school-scoped key and set transaction-local tenant context.
  2. Replay its prior receipt or lock the selected school profile. New mutations require provisioning/active school state.
  3. Resolve every student, year, section and enrollment in that school. New/revised/restored plans require a registered student and a draft year; cancellation still requires a draft year. The section must belong to that exact year.
  4. Check expected versions and planned roll uniqueness. Count planned enrollments against finite section capacity, excluding the current plan when revising. The shared school row lock serializes these writes with academic section changes.
  5. Academic capacity reductions must also refuse a capacity below existing planned reservations. Database administrator SQL remains privileged; these capacity rules govern the protected command workflows.
  6. Commit the domain change, version history, audit and redacted receipt in one transaction; failures roll back all of them. Replays remain harmless even after later status changes.

Verification gates

Stable student/annual identities; duplicate admissions without name-based merging; planned state only; same-school/year keys; unique numeric/label rolls; capacity races and capacity-reduction coordination; cancel/restore history; version races; RLS/no-context/role denial; redacted receipts/output; rollback at history/audit/receipt; private CLI files; unknown/sensitive input rejection and absent HTTP routes. Run the full core suite and fresh migration/rerun harness, then matching-head CI before review. Use the existing Node24/pg/crypto/test runner; no new library is required.
