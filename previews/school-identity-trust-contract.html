Proposed request flow

1. Browser → gateway
One common limiter and route policy.2. Gateway → owner
Private authenticated transport; strip client identity headers.3. Owner → identity
One authenticated introspection call.4. Owner database
Action, relationships, tenant RLS and commit.
  1. The gateway routes only to the destination service. It must not fan a request out to other business services or ask identity to count traffic.
  2. Only an authenticated gateway may forward a browser session to a private domain listener. The owner chooses a configured route profile, required action and its own audience; none is accepted from browser identity headers.
  3. The owner sends the session to identity over an authenticated internal channel. Identity checks the session's selected tenant and current authorization state; a requested tenant must match. School switching remains the existing authenticated rotation workflow.
  4. The owner accepts a fresh response for this outstanding call, then checks domain relationships within its tenant-scoped transaction. No service queries another service's tables.

For a browser mutation, identity must verify the forwarded session-bound CSRF value and exact configured Origin. A trusted route profile determines whether CSRF is required; a caller cannot downgrade a mutation to a read. The gateway must preserve the real Origin and reject ambiguous forwarding headers. Backend ingress authentication and these forwarding rules are integration prerequisites, not implemented features.

Proposed v1 wire contract

POST /internal/v1/session/introspect is a new private endpoint. JSON only, 8 KiB maximum body, Cache-Control: no-store, redacted logs, no redirects and no automatic retries. It must run on a restricted internal listener rather than become a publicly routed auth endpoint.

Caller authentication and audience

Proposed deployment authentication is mutual TLS: validate the peer chain against a configured private CA, certificate validity and the exact allowlisted service identity in SAN. The client validates identity's server name and chain. No wildcard caller match or browser-supplied service-ID override. Map that authenticated caller to its permitted audience and route profiles; reject mismatches. Certificate rotation needs bounded overlap and removal of compromised identities. This infrastructure is not present today and must be reviewed before activation.

The gateway-to-domain path also needs reviewed authenticated transport and private ingress. Existing event/enquiry HMAC credentials cannot automatically authorize user-context forwarding or introspection.

Return an allowed response only after all active-state, tenant-match, action and required CSRF checks pass. UUIDs identify records; they do not authorize access by themselves. Return the single granted action rather than unrelated permissions, role names or memberships. Versions are evidence of the checked snapshot, not a consumer-side revocation feed. Display names, contact data, credentials, raw session/CSRF values and their hashes are excluded.

No portable signing key in v1

The response is authenticated by its direct TLS connection and matched to the outstanding request. It is not a bearer token and must not be forwarded, cached or replayed as an authorization credential. Validate issuer, audience, request ID, route profile, tenant, types and time fields before use. Reject unsupported contract versions or missing/invalid required fields.

If signed assertions are selected in a future version

Use an explicit new contract. Pin the issuer, exact intended audience, allowed algorithm and token type. Resolve kid only from a locally configured issuer key set; reject unknown/revoked keys and never fetch a token-provided URL. Verify signature, issued-at/not-before/expiry and bounded clock skew, plus subject, tenant, session, membership, permission version, requested action and request binding. Specify replay handling, key rotation, compromise response and maximum revoked-access lifetime. A valid signature does not establish current membership or immediate revocation. No signer, JWKS endpoint or JWT consumer is implemented by this proposal.

Freshness and revocation are explicit limits

Proposed initial budgets, pending load validation: a 2-second total introspection deadline, including connection acquisition and database work; a decision admission window of at most 5 seconds from the identity check, capped by absolute and idle session expiry. These are design targets, not measured production guarantees. Align database acquisition, statement cancellation and server timeouts before enabling the contract; today's pool acquisition timeout is 3 seconds and statement timeout is 5 seconds.

  • No positive or negative authorization cache initially. Every new protected request checks the current opaque session.
  • Use a monotonic caller deadline for the HTTP call. Consumers reject expired decisions and malformed/inconsistent timestamps; infrastructure must bound clock skew to at most 1 second. A skew tolerance must never extend the admission expiry.
  • Use the decision immediately for the matched request. If it has expired while queued, obtain a new decision before starting protected work. A request ID alone is not proof of freshness.
  • A revocation committed before the next check prevents that session from being admitted. Identity row locks serialize its own checks against relevant concurrent changes; those locks end with identity's transaction.
  • Already admitted domain work may finish after revocation. A 5-second admission window is not a 5-second commit guarantee. Rechecking just before commit narrows the race but cannot remove it across independent databases.
  • Sensitive irreversible commands need a separately reviewed authorization/commit coordination or fencing protocol if they require stronger revocation semantics. Never claim such guarantees from a version field or a second ordinary HTTP check.
  • Async jobs must reauthorize at execution time under an explicit user-versus-service-job policy. Do not store this transient decision as lasting worker authorization.

Status reactivation needs a policy decision

The current SQL checks active user/tenant status, but the reviewed migrations do not automatically bump a user security version or tenant epoch for every disable/suspend/reactivate transition. Therefore, restoring status can make an otherwise unexpired, unrevoked session usable again. Membership status changes do bump their permission version. Before F02 resumes, choose whether user/tenant suspension must permanently invalidate prior sessions; if yes, add an identity-owned forward migration and explicit suspend/reactivate tests. This is a documented readiness gap, not a code fix included here.

Domain services bound introspection concurrency and circuit breaking as resource protection; the gateway remains the single generic HTTP limiter. Keep prototype auth attempt bounds until mandatory gateway enforcement is in place. Password-hash concurrency remains local.

Identity grants an action; the owner scopes the resource

tenant-user-service

Owns passwords, verified contacts, sessions, selected tenant, memberships, permission grants, invitations/recovery and the internal decision. It must not query student, guardian, teacher, fee or publication tables.

campus-core-api

Resolves the global user/membership reference to its own guardian/student or teacher/class assignments. Check resource access for individual rows, lists, counts, exports, files, searches and jobs. Apply transaction-local tenant context with forced RLS and same-tenant keys after verification.

campus-operations-api

Checks fee/account/receipt ownership, financial permissions, idempotency and its own payment state. A school membership is not permission to refund money or read every ledger.

campus-engagement-api

Checks school publication rights, private-enquiry access, recipient scope, consent and messaging budgets. Internal event-ingestion credentials cannot act as a school admin.

campus-api-gateway

Owns common HTTP counters, routing and secure forwarding. It strips browser identity headers; it does not decide guardian/teacher relationships or proxy business logic through core.

Verified identity membership does not by itself make a core school business profile active. Each domain checks its own lifecycle/entitlement rules. Cross-service IDs are external references, with no shared database foreign keys or copied business ORM entities.

Work remaining before F02 can resume

  1. Review the contract: agree on caller authentication, route-profile registry, exact denial schema, provisional latency/clock budgets and status-reactivation policy.
  2. Identity implementation: add a new narrow SQL decision entrypoint and forward migration, preserving applied checksums and existing function signatures. Return session/version/expiry metadata from the same verification transaction. Keep direct credential/session-table access unavailable to runtime.
  3. Internal transport: configure certificates, caller/audience allowlists, rotation, private listeners, redaction, bounded body/concurrency and cancellation. A health response alone does not establish integration readiness.
  4. Gateway + one consumer: review authenticated forwarding, cookie/Origin/CSRF preservation, selected-tenant matching, consumer response validation and core's resource/RLS checks. Do not enable unrelated private routes.
  5. Meaningful verification: real PostgreSQL tests for the new entrypoint/ACLs and fresh migrations; real internal HTTP/TLS tests for unknown callers, wrong audience/profile, tenant substitution, expiry, stale versions, CSRF, slow/outage/malformed responses and credential redaction; two-service tests for resource isolation and revocation before admission versus work already admitted.
  6. Reviewable delivery: publish owner-specific code PRs with passing build, isolated fresh/security tests and CI. Explicitly resume F02 before product integration; no merge or deployment is authorized by this design document.

Until then: no internal introspection endpoint, no claimed mTLS deployment, no private domain user APIs enabled, no real invitation/recovery provider and no production rollout.
