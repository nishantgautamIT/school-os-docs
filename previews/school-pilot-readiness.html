A pilot with an honest boundary

Use one operator-assisted school workflow before promising a daily school ERP. The audience and evidence requirements change by mode; selecting a mode below does not mark anything ready.

Synthetic, isolated onboarding + intake rehearsal

In scope

  • Two synthetic schools for positive and wrong-school tests.
  • Protected operator provisioning, delivery, text-site publication and gateway public reads.
  • Core draft academic setup, student registration/planning and bounded JSON import.
  • Rehearse public enquiry and private operator follow-up on the linked in-review heads; repeat on merged heads before release.

Outside the claim

  • No live school/parent/student data, public rollout or paid pilot.
  • No school-owner self-service, teacher/parent portal or trusted user forwarding.
  • No active enrollment, automatic lead conversion, payment, live notification, image upload or AI guarantee.

Gate: milestone M1’s cross-service evidence packet, with any pending scenario left explicitly unpassed.

One-school assisted website + admission-enquiry trial

Proposed bounded scope

  • One school, one trained trusted operator and one school content/approval contact; no end-user school accounts.
  • Approved text-first public pages, canonical origin and contact details; operator-managed publish/unpublish.
  • Anonymous minimal admission enquiries through the reviewed gateway; private operator inbox and deliberate follow-up.
  • A short agreed observation window and an explicit volume/retention/support limit; collect actual cost and failure evidence.

Required before real enquiries

  • Enquiry code merged after paired real-database tests and failure/race checks; a usable published-site enquiry form passes browser/CSP/accessibility tests.
  • TLS, private backend ingress, one actual gateway process and correct client/proxy identity.
  • Verified restore, retention/export/deletion and incident/unpublish runbooks.
  • School-approved claims and public contacts; explicit expectations that operators act on behalf of the school.

Not eligible yet. F02 deferral permits this narrow operator model only if private user APIs remain closed and every M2 gate is met.

School-owner, teacher and parent product pilot

This mode is blocked by the user’s explicit F02 integration deferral. Merged standalone auth/session code and a merged HTML trust proposal do not establish authenticated access to core or engagement.

  • Require explicit authorisation to resume F02, then reviewed identity transport, trusted forwarding and fail-closed consumers.
  • Core owns actual guardian/student and staff/class/subject relationships. Section/year relationships are merged; subject-level scope and login binding are not. Identity grants an action, not a domain relationship.
  • Prove selected-tenant/CSRF/session freshness, wrong-school/unrelated-child denial, revocation timing and the suspend/reactivate session policy.
  • Implement and test the actual product UI. Existing HTML concept screens are not a React portal.

Do not put this work into the next two milestones by implication. F10’s paid daily-school pilot still also depends on F06–F09.

Preserve the broader product scope

Inventory/library/procurement/accounting, fees/receipts, homework/attendance, exams/reports, parent messaging, approved media and AI remain roadmap obligations. This deliberately narrow pilot validates an early workflow; it does not redefine the promised integrated product or close F10.

The workflow we need to prove

One school identity flows between service-owned records. Independent databases do not share a SQL transaction. A command label is not an authenticated school-admin identity.

01 · COREProvision a pending school

Profile + audit + outbox commit together. Same-key retries preserve the result.

02 · CORE → ENGAGEMENTDeliver a private seed

Signed delivery + deduplication. Acceptance creates a private draft only.

Text/contact content, expected version and an atomic published revision.

In-review code. Idempotent lead, scoped operator inbox, history and no public contacts.

End-to-end acceptance scenarios

These are future sign-off requirements, not claimed completed tests. Owners supply the implementation and evidence; this planning document does not duplicate their domain design. A01Two-school provisioning and replayCore · Component merged; rehearsal evidence needed.

Set up / exercise

Use synthetic schools A/B and a reviewed protected operator, never real owner contacts. Provision A twice with the same key; try a changed payload and a concurrent duplicate.

Pass condition

One A business profile and its original result/audit/outbox; B remains separate. Conflicts fail without partial writes. Identity link state stays pending.

Evidence to attach

Capture redacted IDs and transaction/assertion results. Existing core tests are component evidence; repeat in the pinned multi-service rehearsal.

A02Seed delivery with lost acknowledgementCore + engagement · Merged transport; paired rehearsal to repeat.

Set up / exercise

Use dedicated event credentials and isolated databases. After engagement commits, lose its acknowledgement, then retry core delivery.

Pass condition

One private draft/inbox/history, no public pages and no identity activation; core eventually records the matching receipt. Bad signature/audience, altered replay and exhausted retries fail safely.

Evidence to attach

Record both build SHAs, isolated database names, transport attempts and final row counts. Earlier paired-test evidence exists; do not treat it as a fresh run here.

A03Publish, update, rollback and removeEngagement + gateway · Component merged; deployment paths still unverified.

Set up / exercise

Complete approved text/contact content through the protected operator; publish via the expected draft version, then change the draft.

Pass condition

Five public pages use one approved revision. Draft changes stay private; failed/stale publish is atomic. Own-school rollback works; other-school revision rejects; unpublish yields next normal gateway GET/HEAD 404.

Evidence to attach

Attach public-read/DB assertions, revision IDs, failure rollback and headers. Verify no student, private owner, token or enquiry data in public HTML.

A04Academic configuration and private boundaryCore · Merged operator capability.

Set up / exercise

Create draft year/class/section records for A and B through the existing operator command. Try stale edits, impossible dates, cross-school references and capacity reductions below plans.

Pass condition

Stable class IDs and year-scoped sections; invalid/racing edits fail atomically, preserving history. Runtime/dispatcher credentials cannot mutate academics. No active-year/portal claim.

Evidence to attach

Use existing academic/people commands; capture school/record/version IDs without real names. Core owns the detailed domain design.

A05New-student JSON preview and atomic acceptanceCore · Merged import; current core main CI has 113 checks including relationships.

Set up / exercise

Private regular 0600 JSON, at most 256 KiB and 1–200 new students, optionally with draft placements. Preview, accept, retry and provoke an expired/changed preview and late row/audit failure.

Pass condition

Preview leaves no student/plan/history domain writes; only its safe receipt persists. Acceptance revalidates capacity/roll/admission rules and commits all or none. Same-key accepted retry returns original IDs; no duplicate admission is merged.

Evidence to attach

Record normalized input hash/count, redacted IDs and rollback assertions. Include a two-school denial and concurrent reservation case. This does not validate CSV/Excel or active enrollment.

A06Public enquiry is admitted only through the common gatewayMain architecture lane: gateway + engagement · Implemented in open gateway #2 + engagement #3; not merged.

Set up / exercise

On the two pinned in-review enquiry heads, use a published A page, exact configured origin and minimal synthetic contact/class fields. Try B substitution, unknown/unpublished slug, bad input and missing required contact permission.

Pass condition

Server-derived site mapping targets A only. Invalid/unpublished requests create no lead. The browser cannot choose a tenant or call the private receiver/operator API. No automatic student, guardian or account creation.

Evidence to attach

Paired real gateway→signed receiver→PostgreSQL test on pinned heads, plus role/RLS assertions. Component forwarding tests alone do not pass this case.

A07Enquiry exact retry, conflict and publication raceGateway + engagement · In-review implementation; owner-reported local paired smoke, broader rehearsal pending.

Set up / exercise

Lose the acknowledgement after a committed enquiry; retry the same submission, then change its payload under the same identity. Race publication/unpublish according to the owning contract.

Pass condition

One accepted lead/history with stable redacted acknowledgement. Exact replay is safe; conflicting reuse rejects. Unpublished-school behavior follows the agreed owner contract with no accidental public contact leakage.

Evidence to attach

Paired tests must include concurrent requests, commit-before-ack, revalidation and transactional failure. Do not invent a second enquiry protocol in this plan.

A08Abuse, timeout and secret boundariesGateway + engagement + release · Public reads merged; write/deployment gates pending.

Set up / exercise

Try wrong origin, forged user/tenant headers, oversized or slow bodies, invalid signature, rate/counter exhaustion, upstream timeout and direct backend access. Repeat local key setup.

Pass condition

Bounded fail-closed decisions; no bypass, raw contact/token logs or reflected request payloads. Dedicated enquiry keys cannot act as core-event/admin credentials. Setup repeat and absolute body-read deadlines must pass.

Evidence to attach

Record expected response classes and zero/one-row outcomes, cancellation behavior and deployed firewall/proxy checks. One-process memory budgets are not shared multi-replica limits.

A09Private admissions follow-upEngagement · Protected operator inbox implemented in engagement #3; in review.

Set up / exercise

Use the protected operator inbox for A; try a B record, stale update and unsupported transition. Trace a valid follow-up.

Pass condition

A-scoped operator workflow, expected versions and actor/reason history; public/runtime roles cannot list leads or read contacts. Operator labels remain labels, not signed-in school-staff identities.

Evidence to attach

Verify owning implementation’s actual transitions/ACLs. Capture redacted command receipts and row-level denial, not screenshots of real contacts.

A10Explicit intake-to-core handoffEngagement + core · Operator core available; automated bridge missing.

Set up / exercise

After a school reviews a synthetic lead, have an authorised operator deliberately register/import a new student under the correct core school.

Pass condition

Human-reviewed reference/handoff only. A contact match or enquiry does not prove guardian identity or create a verified relationship. Core admission duplicate checks remain authoritative.

Evidence to attach

Record the reviewed handoff and separate core receipt; a manual demonstration must not be called a shipped cross-service conversion API.

A12Restore and reconcile the pilot workflowRelease + service owners · No complete pilot restore evidence reviewed.

Back up each service-owned database/configuration safely and restore into isolated scratch targets. Never delete/recreate existing development or pilot volumes to demonstrate success.

Pass condition

Recover the chosen school’s core IDs/plans, public revision and private enquiry/history; reconcile transport inbox/outbox without duplicates. Restored public/private privileges and unpublish behavior remain correct.

Evidence to attach

Attach timed restore report, row/integrity/privilege assertions, backup age and an agreed recovery-point/time target. No cross-database atomic snapshot is assumed.

A13Real ingress, load bounds and support stop switchRelease + gateway/engagement · Deployment and load evidence missing.

Set up / exercise

Use the intended TLS hostname, blocked direct backend listeners and exactly one gateway process. Exercise configured bursts, slow requests, restarts and outage recovery.

Pass condition

No frontend-to-backend bypass; bounded queue/pool/concurrency and predictable 429/503/timeouts. Resolve trusted-proxy client identity before deploying behind a proxy; ignored forwarding headers can collapse clients into one bucket.

Evidence to attach

Measure p95 latency, error/queue/counter capacity, restart behavior and actual infrastructure/support cost against a written workload. Agree thresholds before testing; do not infer school capacity from test counts.

A clearly described operator-assisted website/intake trial, with no promised parent/staff portal, payments or real messaging. Collect only necessary enquiry data after privacy/access/recovery controls pass.

Evidence to attach

School-approved content record, support runbook and verified data lifecycle. Use synthetic contacts until the full conditional public-pilot gate passes.

Sequence by evidence, not calendar promises. Estimate dates after owner PRs and the paired harness are reviewable. Neither milestone resumes F02 or closes the broad paid-pilot issue.

M1 · CONTROLLED REHEARSAL

Prove one synthetic school intake journey, with a second school as the denial fixture.

Finish the enquiry vertical slice in its owning lane, then combine merged provisioning/delivery/publication/gateway and core planning/import.

  1. Review the existing enquiry owner PRs and their matching-head CI/fresh-install evidence; repeat their local paired smoke and record exact heads. Pending work remains visibly pending until merged.
  2. Pass A01–A10 on a pinned, isolated multi-service setup. Include exact retries, lost acknowledgements, wrong-school attempts, stale edits and atomic rollback.

Exit artifact: reproducible acceptance report + reviewed runbook. Decision: eligible to assess M2 gates, not to launch a staff/parent portal. Core owns academics/intake planning; the main architecture lane owns enquiry/gateway code; product planning owns the acceptance decision.
M2 · LIMITED PUBLIC INTAKE TRIAL

Admit one real school only after ingress, recovery and data-operation controls pass.

Provide an operator-assisted text website and enquiry follow-up. No end-user login, payment or outbound message promise.

  1. Owner PRs from M1 are merged; add the missing visitor enquiry form and validate browser consent, errors, retry, accessibility and CSP. Rerun A03 and A06–A09 through the deployment, then pass A12–A14.
  2. Record actual proxy/client identity, backend isolation, TLS, secret/key rotation, one-process topology and a safe stop/unpublish path.
  3. Prove scratch restore/reconciliation and the enquiry retention/export/deletion procedure. Obtain school approval of content, access, support and trial limits.
  4. Agree workload/error/latency targets before testing; monitor incidents, enquiry acknowledgement/follow-up failures and real operating/support cost during the bounded trial.
  5. End with a school review and go/hold/stop decision. Any unpassed blocker means the trial remains synthetic or read-only, without accepting real enquiry data.
Exit artifact: signed-off pilot evidence and measured operational results. Decision: whether to continue the narrow trial. A broader authenticated/paid pilot needs an explicit later F02 scope decision and remaining F06–F10 delivery.
