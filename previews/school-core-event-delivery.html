F04 · Core → engagement · 25 October 2026

Create once.
Deliver safely, even after a retry.

A core-owned outbox worker sends one versioned school-profile event to a separate private engagement receiver. Service-owned databases and credentials remain independent.

One workflow, two commits

  1. Core school provisioning commits its pending profile, audit, result and outbox event together.
  2. The core worker claims a due event with a short database lease and SKIP LOCKED, then releases the transaction before HTTP.
  3. The receiver authenticates the raw body and validates the exact event contract. Engagement commits the private draft, event inbox, command receipt and audit together.
  4. The receiver acknowledges the exact event and tenant only after commit. Core marks delivery complete only when that matching acknowledgement arrives and it still owns the lease.

A dropped response can cause another send after the lease expires. Inbox/request deduplication gives one committed draft, not exactly-once network delivery. A delivery receipt does not activate identity or publish the site.

Private transport contract

POST /internal/core-events accepts only an envelope with type school.profile_provisioned.v1 and the existing six-field seed payload. HMAC-SHA256 binds a fixed protocol/audience prefix, timestamp, method, exact path and raw UTF-8 body. Key IDs support at most two keys for rotation; signatures use constant-time comparison and a five-minute clock window. Every retry receives a fresh timestamp/signature while preserving its event ID. Persistent event deduplication makes valid replays harmless.

Use HTTPS for the fixed configured destination; only loopback HTTP is permitted outside production. Reject redirects, credentials, query strings and alternate paths. Deploy the receiver behind private ingress/TLS termination. Its optional bind address is loopback by default; it is never added to public website routes or the browser gateway. HMAC authenticates this narrow core publisher, not human users or arbitrary service actions.

Least-privilege processes

Core HTTP process

Existing restricted runtime credentials. No event signing key or dispatcher credentials.

Core delivery worker

A dedicated role reads approved outbox seeds across schools and updates only delivery metadata. It cannot edit payloads, school profiles, users or security evidence. No engagement database connection.

Engagement receiver

A dedicated role may insert an initial site/draft, ingest audit and deduplication records. No UPDATE/DELETE, revision/public-page writes, private draft SELECT or migration credentials. No core database connection. Public HTTP retains projection-only credentials.

Bootstrap provisions cluster roles; forward-only migrations grant the narrow table/column policies. Existing applied migrations remain unchanged. Public ingress/common rate-limit work and authenticated admin authorization remain pending.

Failure and recovery rules

One sequential request per worker; thirty-second leases, five-second bounded requests/responses, and at most eight delivery attempts. Retriable transport/server/auth failures use persisted exponential backoff with jitter. Invalid payloads, rejected conflicts and redirects become terminal failures. Exhausted/crashed final leases become dead-letter state on the next scan. No automatic infinite retries.

Lease tokens fence stale workers from settling a newer attempt. Matching committed acknowledgements alone set delivered_at. A protected operator redrive resets only a non-leased dead event without changing its event ID/payload; after fixing the cause, engagement deduplication still protects against duplicate drafts. Logs/status contain event IDs and short failure codes, never keys, connection strings or remote bodies.

Verification gates

Real PostgreSQL checks cover dedicated-role denial, concurrent claims, lease expiry/fencing, persisted backoff, exhaustion/redrive, HTTP timeout/redirect/ack mismatch, signature/path/body/timestamp/key rotation, oversized input, duplicate delivery, changed-payload conflicts and public-route isolation. A real two-database HTTP smoke test must prove core provisioning → one private engagement draft → core delivery receipt, including lost-ack retry. Fresh migrations and repository CI must pass before review.
