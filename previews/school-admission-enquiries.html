Submit once.
Keep the conversation private.

One workflow: public enquiry through the shared gateway → authenticated private engagement receiver → school-scoped operator inbox.

Submission contract

POST /schools/:slug/enquiries accepts bounded JSON and a UUID Idempotency-Key. Require the configured exact browser Origin, explicit contact consent and an adult-contact declaration. Fields: contactName, Indian mobile phone, optional email, interest and message. No tenant ID, student name/date-of-birth fields, attachments or message sends. Declarations are not identity/age verification or a legal-compliance claim.

Engagement resolves the tenant from the published contact projection, takes the same school advisory lock as publication, rechecks publication and commits the enquiry, receipt and audit together. Unpublished/unknown schools reject new submissions. An exact retry returns the original generic202 receipt even after unpublish; changed reuse returns409. The key is scoped to school slug. Public replies contain no contact data, inbox content or private record ID.

One common rate-limit implementation

Keep the existing general gateway budgets. Reuse its token-bucket engine for stricter submission policies: global60/refill1 per second; client5/refill1 per60 seconds; school30/refill1 per10 seconds; client-school3/refill1 per300 seconds. Retry attempts also consume submission budgets. Denial happens before reading/forwarding the body. Both maps are bounded; expiry is at least the full refill lifetime so eviction cannot reset a depleted long budget. Distributed Redis/proxy trust remain pending; one gateway process only.

Prevent write-route bypass

The public engagement page listener stays read-only. A separate private enquiry listener (loopback3004 by default) uses a dedicated insert-only role. The gateway signs the raw body, internal path, timestamp and idempotency key with a dedicated HMAC key/purpose. The receiver verifies it before database work; ordinary direct clients cannot submit accepted writes. Never reuse core-event keys. Support at most two verification keys for rotation and a five-minute timestamp window.

The gateway holds no database credentials. The receiver cannot read enquiry contacts, edit/delete enquiries, publish, read drafts or migrate. Local body/concurrency limits are resource guards, not duplicate generic rate counters. HTTPS/private ingress and secret management remain rollout requirements; cryptographic authentication protects this write path even if a direct caller can reach the receiver.

Private records and handling

New engagement tables: admission_enquiries (school, approved source revision, adult contact fields, consent declaration, status/version), enquiry_receipts (slug/key, digest and private linkage, no contacts), enquiry_audit (school-scoped received/read/status-change evidence, no contact payload). Enquiries and audit force RLS with same-school keys. Published pages and event payloads never contain enquiry contacts.

Protected operator commands list a school's inbox and change new/contacted/closed status with expected version, operator label and reason. Private results go to a new0600 JSON file; stdout contains only a count/status summary. Read/status actions are audited. No public/private inbox HTTP route or automatic WhatsApp/SMS/email is enabled. A submitted enquiry does not enroll a student.

Boundaries and verification

8 KiB JSON, strict unknown-field rejection, bounded text and phone/email normalization, no arbitrary HTML execution. Gateway Origin checks and HMAC are distinct from human authentication; anonymous bots still require policy/production abuse tuning. Retention/privacy operations and real school-admin access must be reviewed before a production pilot.

Verify real PostgreSQL isolation/privileges, lost-ack replay and conflicts, publication/unpublish races, bad signatures/origins/body limits, submit-specific budgets, private operator handling and no contact leakage. Run a real gateway → receiver → PostgreSQL → operator inbox integration check. Design recorded before implementation. Full F04 remains open; no automatic merge/deployment.

Run the private workflow

In engagement, run npm run db:up, npm run db:migrate and npm run build. Build the matching gateway enquiry branch and run its npm run enquiries:configure-local -- ../campus-engagement-api helper to create/preserve dedicated signing keys in ignored private profiles. Start engagement with npm run enquiries:receive on loopback 3004; start the gateway separately. The public page listener remains on 3002, core-event receiver on 3003, PostgreSQL on 55435.

From engagement, use npm run enquiries:admin -- /private/command.json /private/new-result.json. The command is a nonsymlink regular 0600 JSON file, at most 4 KiB, with action, tenantId, operatorRef and reason. List accepts limit (default 25/max 50) and before (nextCursor); read accepts enquiryId; status accepts enquiryId, expectedVersion and new/contacted/closed. Returned contacts remain in the new 0600 result file. If output fails after commit, inspect the inbox before retrying; old-version status retries conflict.

Managed environments must provide the dedicated enquiry database credential and one or two verification keys via private secret configuration, restrict internal ingress, and terminate TLS. The receiver authenticates the gateway service; it does not authenticate a person or grant school-admin access.

Frozen wire contract

HMAC-SHA256 signs UTF-8 prefix and unchanged raw body bytes. Headers are x-enquiry-key-id, x-enquiry-timestamp, x-enquiry-signature and idempotency-key. The signed purpose separates this audience from core events. A timestamp may differ by at most 300 seconds; UUID and key fields reject trailing line terminators.

campus-enquiries-v1\n
TIMESTAMP\n
POST\n
/internal/enquiries/SLUG\n
REQUEST_UUID\n
RAW_BODY_BYTES

Cross-service fixture: key = 32 bytes of hexadecimal 01; timestamp 1793641800; slug synthetic-school; UUID 11111111-1111-4111-8111-111111111111; raw UTF-8 JSON {"message":"नमस्ते"}. Expected signature:

6c6159a105b23518026fd67b7a103c1bee8b23b607d21c0ab739cfb8d03dec06

This synthetic key is only a frozen test vector; local and deployed configurations use separate random keys.
